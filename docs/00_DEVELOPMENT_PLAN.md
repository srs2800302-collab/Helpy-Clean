# Helpy — порядок разработки

## 1. Статус документа

Документ определяет рабочую последовательность разработки Helpy.

Он не заменяет утверждённые бизнес-требования, Registry и решения владельца.

## 2. Решение по изоляции новой реализации

Первоначальный вариант с отдельной веткой старого репозитория отменён.

Принято:

- отдельный независимый Git-репозиторий;
- отсутствие Git ancestry старой реализации;
- отсутствие копирования legacy source code;
- старая реализация используется только как источник информации для чтения;
- новая реализация пишется заново.

Это изменение касается только способа изоляции разработки.

## 3. Общая последовательность

1. Этап 0 — подготовка независимой базы разработки.
2. Этап 1 — основной архитектурный фундамент.
3. Этап 2 — ядро административного управления.
4. Этап 3 — каталог, конструкторы и динамические формы.
5. Этап 4 — аккаунты и управление заказами.
6. Этап 5 — предложения, переговоры и Final Agreed Price.
7. Этап 6 — оплата и назначение мастера.
8. Этап 7 — работа, доказательства и завершение.
9. Этап 8 — отмены, урегулирование, задолженности и выплаты.
10. Этап 9 — оставшаяся продуктовая функциональность.
11. Этап 10 — интеграционные испытания и подготовка к выпуску.

Порядок изменяется только отдельным решением владельца.

## Сквозное требование — мультиязычность

Весь пользовательский интерфейс Mobile и Admin должен поддерживать:

- Thai (`TH`);
- Russian (`RU`);
- English (`EN`).

Пользователь Mobile и пользователь Admin самостоятельно выбирают язык интерфейса.

Переключение между любыми двумя языками из TH / RU / EN должно выполняться в обоих направлениях немедленно, без перезапуска и пересборки, и переотображать на выбранном языке:

- весь Mobile UI;
- весь Admin UI;
- системные тексты;
- опубликованный динамический контент;
- Registry, категории, вопросы, правила и подсказки;
- Dynamic Form Engine;
- временный pre-selection chat;
- постоянный рабочий chat;
- уже загруженные сообщения обоих chats.

Оригинальный текст пользовательского сообщения сохраняется неизменным.

Перевод сообщения является отдельным представлением оригинала на выбранном пользователем языке.

Admin должен позволять создавать, редактировать и публиковать предусмотренный пользовательский контент на TH / RU / EN.

Механизм локализации и перевода должен быть общим и не реализовываться отдельно внутри каждого feature.

Каждый новый пользовательский feature должен поддерживать TH / RU / EN непосредственно при его реализации, а не отдельным завершающим проходом.

## 4. Этап 0

Результат Этапа 0:

- независимый Git-репозиторий;
- принятая документация разработки;
- отсутствие product implementation;
- отсутствие зависимости от конкретной рабочей станции;
- отсутствие GitHub remote до отдельного разрешения владельца.

## 5. Этап 1 — основной архитектурный фундамент

Этап 1 является одним общим фундаментом и состоит из:

`F1 → F2 → F3 → F4 → F5`

F1–F5 не являются отдельными продуктами.

### F1 — Clean Structure

Создать независимые основы:

- Mobile;
- Backend;
- Admin;
- Shared API Contracts.

Создать общую архитектурную основу локализации TH / RU / EN, хранения выбранного пользователем языка и дальнейшего подключения перевода переписки без feature-specific localization logic.
Обеспечить реальные точки запуска, build/test tooling, CI и изоляцию от legacy implementation.

### F2 — Domain Core

Создать независимые:

- Entities;
- Repository Interfaces;
- UseCases;
- typed Failures;
- configuration contracts.

Domain тестируется без Cloudflare Worker, D1, Flutter UI и Admin UI.

### F3 — Backend + Database

Подключить:

- Cloudflare Worker как первоначальный server adapter;
- D1 как первоначальный database adapter;
- migrations;
- API;
- persistence adapters;
- обработку ошибок.

Domain не зависит от Worker или D1.

### F4 — Flutter + Admin

Подключить:

- Flutter;
- Clean Architecture;
- Bloc/Cubit;
- Dependency Injection;
- typed API client;
- защищённый Admin;
- Draft / Published;
- динамическую конфигурацию.

Mobile и Admin поддерживают TH / RU / EN и позволяют пользователю самостоятельно переключать язык интерфейса без перезапуска и пересборки. Admin также должен позволять создавать, редактировать и публиковать предусмотренный пользовательский контент на всех трёх языках.
Опубликованное через Admin изменение разрешённого текста или настройки должно быть доступно Mobile через API без пересборки.

### F5 — Integration Acceptance

Проверить:

- взаимодействие компонентов;
- security;
- отказоустойчивость;
- переносимость;
- архитектурные границы;
- динамическую конфигурацию;
- Admin с изолированной административной границей доступа, подготовленной к полноценной authentication и authorization на Этапе 2;
- заменяемость Infrastructure adapters.

### Пять обязательных свойств приёмки Этапа 1

Этап 1 не принимается, пока не доказано одновременно:

1. Mobile, Backend и Admin запускаются независимо и взаимодействуют через согласованный API.
2. Business logic не импортирует Cloudflare SDK, D1 или UI.
3. Изменяемые настройки и тексты не зашиты в executable code как неизменяемые бизнес-значения.
4. Все три компонента имеют реальные проверки, а не фиктивные успешные команды.
5. Новый функциональный модуль можно добавить без изменения существующего архитектурного ядра.

## 6. Этап 2 — ядро административного управления

Реализовать:

- административную authentication;
- разграничение прав;
- versioned configuration;
- Draft / Published;
- журнал изменений;
- API настроек;
- динамический контент и страницы.

Обязательная проверка:

изменить опубликованный текст или настройку через Admin и получить изменение в Mobile без пересборки.

## 7. Этап 3 — каталог, конструкторы и динамические формы

Реализовать:

- утверждённый Registry;
- категории;
- зависимые вопросы;
- фотографии;
- правила;
- подсказки;
- административные конструкторы;
- Dynamic Form Engine.

Registry, категории, вопросы, правила, подсказки и публикуемый пользовательский контент должны поддерживать TH / RU / EN; Dynamic Form Engine формирует интерфейс на текущем выбранном языке пользователя.
Восстановить из утверждённого Registry актуальный бизнес-смысл категорий, сущностей, вопросов, правил и связей; спроектировать и реализовать их заново в новой архитектуре без копирования legacy schema, code или contracts.
Формы строятся по опубликованным данным, а не по category-specific hardcode.

## 8. Этап 4 — аккаунты и управление заказами

Реализовать:

- вход;
- профили клиента и мастера;
- роли;
- специализации;
- создание и публикацию заказа;
- сохранение редакций;
- допуск подходящих мастеров.

## 9. Этап 5 — предложения, переговоры и Final Agreed Price

Реализовать:

- предложения мастеров;
- временные pre-selection chats;
- таймеры;
- однократное обоснованное изменение цены мастером;
- подтверждение цены клиентом;
- Final Agreed Price;
- финансовый snapshot.

Временный pre-selection chat использует общий механизм перевода переписки и немедленно переотображает уже загруженные сообщения при смене выбранного пользователем языка. Оригинальный текст сообщений сохраняется неизменным.

## 10. Этап 6 — оплата и назначение мастера

Реализовать:

- наличный и безналичный маршруты;
- комиссию от Final Agreed Price;
- payment states;
- provider confirmations;
- назначение мастера;
- защиту от двойных операций.

Изменение комиссии не меняет ранее зафиксированные финансовые условия.

## 11. Этап 7 — работа, доказательства и завершение

Реализовать:

- постоянный рабочий chat;
- фотографии;
- подтверждение результата;
- исправления;
- завершение заказа;
- историю действий.

Постоянный рабочий chat использует тот же общий механизм локализации и перевода, что и временный pre-selection chat, и немедленно переотображает уже загруженные сообщения при смене выбранного пользователем языка. Оригинальный текст сообщений сохраняется неизменным.

## 12. Этап 8 — отмены, урегулирование, задолженности и выплаты

Реализовать:

- утверждённые варианты отмен;
- компенсации;
- административные решения;
- задолженности мастера;
- погашение долга;
- выплаты.

## 13. Этап 9 — оставшаяся продуктовая функциональность

Реализовать утверждённый состав первого выпуска:

- отзывы;
- рейтинг качества;
- показатель надёжности;
- notifications;
- сообщения Helpy;
- обратную связь;
- content pages;
- акции;
- promo codes;
- скидки.

## 14. Этап 10 — интеграционные испытания и подготовка к выпуску

Проверить:

- end-to-end сценарии;
- security;
- согласованность данных;
- отказоустойчивость;
- сохранение конфигурации;
- recovery;
- Android build;
- Admin;
- первоначальное deployment.

Проверить переключение между любыми двумя языками из TH / RU / EN в обоих направлениях без перезапуска и пересборки с немедленным переотображением Mobile UI, Admin UI, динамических форм, опубликованного контента, временного и постоянного chats, включая уже загруженные сообщения.
Отдельно проверить замену server и database adapters без изменения Domain.

## 15. Причина порядка

Admin и динамическая конфигурация создаются сразу после фундамента.

Это предотвращает первоначальное размещение форм, правил, комиссий, изменяемых текстов и страниц в hardcode с последующей переработкой.

Legacy architecture не переносится ради ускорения.

## 16. Правила выполнения

Каждый этап проходит:

`диагностика → реализация → независимые проверки → доказательный отчёт → приёмка владельцем`

PASS допускается только при наличии доказательств.

Ранее принятые решения не изменяются под видом технической оптимизации.

Каждый Git commit должен соответствовать конкретной выполненной задаче.

Публикация в GitHub выполняется только после отдельного разрешения владельца.
