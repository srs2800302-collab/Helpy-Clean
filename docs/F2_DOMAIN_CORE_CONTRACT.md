# HELPY CLEAN — F2 Domain Core

**Редакция:** R34 от 17.11.2026.

**Статус:** утверждён владельцем. DOCUMENT GATE = PASS. Реализация F2 разрешена.

**Назначение:** единый обязательный нормативный контракт реализации и приёмки F2 в репозитории `Helpy-Clean`.

**Основание:** принятый F1, утверждённая бизнес-модель Helpy и архитектурные принципы новой независимой реализации.

## 1. Область F2 и иерархия требований

F2 создаёт заново **исполняемый и независимо тестируемый серверный Domain Core на TypeScript** в уже принятом контуре `CLEAN_ROOT/apps/backend`: Entities, Repository Interfaces, UseCases, typed Failures и configuration contracts. Обязательны реальные доменные правила, а не пустые DTO/интерфейсы. Это уточнение языка **не изменяет принятый F1**.

**Единый исполнитель критических бизнес-операций:** серверные `Domain`/`Application` решают вопросы назначения мастера, денежных обязательств, оплаты, долгов, отзывов, санкций, Admin Resolution и прав доступа. Flutter/Dart является клиентом через типизированные Shared API Contracts и сохраняет собственную Clean Architecture (`Data`/`Domain`/`Presentation`, Bloc/Cubit), но не становится второй независимой реализацией серверных инвариантов. UI-предвалидация не заменяет серверную проверку. В F2 **не требуется писать второй Dart Domain Core** или расширять Mobile UI; будущие клиентские UseCases разрабатываются на соответствующем этапе по F1.

- В F2: чистые модели категорий, сущностей, сценариев, динамических правил форм, заказов, специализаций, ценовых предложений, чатов, оплаты, задолженности; проверки, переходы и доменные события.
- **Не в F2:** реализация Admin-конструкторов, экранов Flutter, Worker/D1, миграций, API, платежного провайдера, фактического хранения/передачи сообщений и файлов. Доменные контракты для будущих этапов определяются в F2.
- Приоритет при исполнении F2: настоящий контракт после приёмки владельцем содержит действующие бизнес-решения; последующее явное решение владельца применяется после согласования изменения контракта. Документы принятого `Helpy-Clean` определяют технические границы F1; Registry предоставляет только адресные предметные данные по §2.1. Если F2 явно заменяет или исключает историческое правило, применять F2 без повторного согласования. При действительном пробеле или противоречии действующих требований — §14; **не сочинять** бизнес-поведение.
- Для чтения источников исполнитель использует **два независимых подтверждённых локальных корня**: `CLEAN_ROOT` (новый `Helpy-Clean`, нормативные документы и новый код) и `LEGACY_ROOT` (старый `Helpy`, только read-only справка). Относительные пути в §2.1 и §15 разрешаются только относительно указанного корня. Для `LEGACY_ROOT` единственная разрешённая область чтения — 42 диапазона (31 + 11) в §2.1 через локальный CodeReview; иные legacy-файлы и диапазоны не читать. Не искать эти документы через web/браузер или GitHub и не требовать checkout исторического commit; отсутствие локального источника регистрируется как входной пробел, а не компенсируется выдуманными правилами.
- Запрещены копирование legacy-кода, схем БД, старых API, структуры каталогов, Git history; запрещены hardcoded Admin-параметры. Бизнес-смысл старого Registry читается и адаптируется под утверждённые правила.
- Серверные `Domain`/`Application` (TypeScript) независимы от Node.js, Cloudflare Worker, D1, Flutter, HTTP, БД, внешних SDK и платёжных/переводческих провайдеров. Направление зависимостей: транспорт и инфраструктурные адаптеры → Application → Domain; порты принадлежат внутренним слоям. Проверки должны выполняться с подменяемыми Clock, repositories и provider ports.
- **Портируемость:** первоначальные `Cloudflare Worker + D1` реализуются только как внешние адаптеры на F3. Переезд на другую площадку/СУБД требует замены адаптеров и миграции данных, но не переписывания Domain/Application и правил продукта. В F2 запрещена зависимость доменных типов, UseCases и тестов от Worker/D1/Node runtime globals.
- `CLEAN_ROOT/packages/contracts` содержит уже созданную в F1 границу обменных типов TypeScript/Dart. Wire DTO не становятся Domain Entities; server-only состояния и проверки прав не делегируются клиенту. При необходимости расширять типизированные контракты по принятой структуре, без копирования бизнес-алгоритмов в Dart.

### 2.2. Утверждённые внутренние архитектуры восьми корневых категорий

Корневое расположение категории и её внутренняя форма заказа — **разные измерения**. Все восемь категорий являются самостоятельными корневыми узлами, но сохраняют уже утверждённую для каждой бизнес-архитектуру. Нельзя унифицировать их в одну схему лишь ради одинакового интерфейса.

| Корневая категория | Архитектурный профиль и принадлежность mini-ТЗ |
|---|---|
| Air Conditioning | **Scenario-first Mini-TZ**: `Service`, `Install & Connect`, `Replacement` — три самостоятельные сущности/услуги со своими формами. |
| Cleaning | **Terminal Mini-TZ**: три самостоятельные сущности уборки; искусственный общий `install/replace` не вводится. |
| Plumbing | **Equipment Mini-TZ / internal scenarios**: кран, унитаз, электрический душ; у каждой сущности собственные `install_connect` и `replace`. |
| Electrical | **Repeatable-point Mini-Scope**: заказ содержит одну или несколько электрических точек; у каждой — тип оборудования, тип работы, ответы и свои запросы фотографий. **Число точек** не равно **количеству изделий в точке**. `Add More` создаёт следующую точку, а не увеличивает количество изделий текущей. |
| Locks | **Equipment Mini-TZ / internal scenarios** по последнему решению: две сущности (межкомнатный дверной и мебельный замок); в каждой установка и замена. Исторические четыре отдельные action-entities только источник содержания этих сценариев. |
| Furniture Assembly | **Structured Mini-TZ**: четыре самостоятельные сущности; таблицы/перечни/замеры принадлежат собственному mini-ТЗ, не становятся дочерними бизнес-сущностями и не превращаются в `Mini-Scope`. |
| Appliance | **Equipment Mini-TZ / internal scenarios**: три сущности с установкой и заменой; вопрос о встроенности маршрутизирует в другую **корневую** категорию, не создаёт вложенность. |
| Built-in Appliances | **Equipment-list Mini-Scope**: самостоятельная восьмая корневая категория с прежней внутренней архитектурой списка оборудования. В одном заказе несколько приборов, каждый со своей сервисной сущностью, сценарием и mini-ТЗ. Общий механизм выбора типа работ может располагаться на уровне mini-scope; выбранное действие фиксируется **для каждой единицы оборудования**, поэтому в одном заказе допустимы одновременно установка одного прибора и замена другого. |

**Обязательная семантика Domain:** `Category` → разрешённая внутренняя конфигурация → конкретная `ServiceEntity`/элемент `MiniScope` → выбранный `Scenario` → принадлежащие ему вопросы, фото-запросы, таблицы и информационные блоки. Физическая глубина заголовков прежнего Markdown и устаревший `parentNodeId` не определяют новую бизнес-иерархию. Никаких category-specific `switch` по отображаемому названию.

**Идентичность:** у категорий, сущностей, сценариев, элементов mini-ТЗ и переиспользуемых блоков — стабильные идентификаторы, не зависящие от `TH/RU/EN` названия, отображаемого порядка или перевода. `service`, `install_connect`, `replace`, `relocate` — семантические ключи действий, не переведённые названия. Новые стабильные идентификаторы проектируются с нуля. Предметные соответствия устанавливаются по таблице 8/31 и разрешённым диапазонам §2.1; старые `nodeId`, `headingPath` и identity-ledger не требуются и не являются источником идентичности новой системы. Не читать внешние identity-ledger или дополнительные legacy-фрагменты.

**Версии и снимки:** при публикации заказа сохраняется редакция каталога и разрешённые связи/значения каждого mini-ТЗ; при поздних изменениях через Admin историческое ТЗ и обязательства сторон не пересчитываются. Проверки F2 обязаны охватывать все восемь архитектурных профилей, обе разновидности кратности Electrical и независимые сценарии в Built-in Appliances.

### 2.3. Управление каталогом из Admin

Для категорий и сущностей обязательны авторизованные операции создания, редактирования, публикации, отключения публикации, повторной публикации, удаления из действующего каталога и изменения порядка отображения; порядок корневых категорий и порядок сущностей внутри каждой категории задаются независимо. Названия и описания редактируются по §3.3. Изменения действуют через версионированные Draft/Published данные, без пересборки. Отключение категории исключает её содержимое из действующего каталога; отключение отдельной сущности не выключает остальные. Повторная публикация допускается только для валидной конфигурации; не включает ранее независимо отключённые сущности. Удаление из действующего каталога не уничтожает исторические ID, редакции, заказы и их ссылки; битые активные маршруты/связи не публикуются. Порядок и локализация не меняют identity. Эти операции не отменяют и не изменяют уже опубликованные заказы (§4). F2 реализует модели, авторизованные операции, порты, typed Failures и тесты; UI, persistence и наполнение — последующие этапы.

## 3. Конфигурация форм, фотографии, информация и перевод

1. Сущность может иметь ноль вопросов, фото-запросов или информационных блоков; каждый блок независим и определяется опубликованной конфигурацией сценария.
2. Активные обязательные вопросы/запросы фотографий блокируют публикацию, пока не удовлетворены; необязательные пропускаются. Проверяется формат и наличие файлов, **не достоверность их содержания**. Конкретные количества файлов — конфигурация, не лимит Domain Core.
3. Зависимые вопросы изменяют набор полей внутри формы. Маршрутизирующие вопросы направляют к другой сущности/корневой категории по конфигурационному ID, без создания ошибочного заказа. Утверждённый пример: обычная стиральная/посудомоечная машина, «Техника встроенная?» = «Да» → Built-in Appliances.
4. Поддержать типизированные повторяемые таблицы мебели; фиксированную таблицу замеров встроенной мебели (6 ширин, 2 высоты, 6 глубин); самостоятельные мини-ТЗ каждой электрической точки и единицы встроенной техники. Для Cabinet Furniture и Furniture Disassembly первоначально по три строки, добавление строк без фиксированного максимума.
5. ТЗ отдельно от информационных блоков. Для текущей роли доступно действие «Информация по заказу». Общие и особые блоки переиспользуются. При первоначальном наполнении сохраняется утверждённый смысл; языковые редакции и их управление — §3.2–§3.3.
6. Точная утверждённая формулировка: «При замене демонтированное оборудование остаётся собственностью клиента и остаётся на объекте, если стороны не согласовали иное».
7. Admin меняет содержание, языковые редакции, вопросы, варианты ответов, фото-запросы, правила связей и порядок без пересборки приложения. Публикация и исторические версии — §2.3, §3.2–§3.3.
8. Оригинал сообщений неизменен; TH/RU/EN перевод — отдельное представление. Один общий механизм перевода сообщений для всех контекстов чата, независимый от провайдера. Распределение ответственности контента, интерфейса и переписки определяется только §3.3.

### 3.1. Переключение языка интерфейса — Mobile и Admin

- **Единый видимый способ выбора языка:** иконка глобуса в **правом верхнем углу интерфейса**. По нажатию открывается список выбора языка; порядок пунктов строго **ไทย → Русский → English** (тайский, русский, английский). Исходные скриншоты подтверждают выбранный образец расположения и раскрывающегося меню.
- Этот принцип обязателен **для публичной части Mobile** (в том числе до входа/регистрации) **и для интерфейса Admin Panel**. Выбор языка не связан со способом входа, активной ролью, специализацией мастера или фильтром заказов.
- Переключение обновляет локализованные элементы соответствующего интерфейса без повторной авторизации и без изменения канонических бизнес-данных. Список доступных локалей архитектурно расширяем; обязательный набор запуска и его порядок — `th`, `ru`, `en`. Конфигурация доступности и порядка UI-языков не определяет набор обязательных языковых редакций для публикации: все три языка обязательны по §3.3, их исключение из обязательного набора не является Admin-настройкой. UI не должен отображать английские технические идентификаторы вместо перевода.
- **Граница F2:** Domain Core предоставляет типизированный контракт доступных локалей, выбранной локали и независимых переводов, но **не создаёт Flutter-виджеты и Admin UI**. Иконка, позиционирование и открытие меню реализуются на соответствующих UI-этапах. Это обязательное UI-требование для этих этапов, а не задача рисовать интерфейс в F2.


### 3.2. Единая модель хранения и переиспользования правил и информационных блоков

**Правила клиента и мастера — самостоятельные конфигурационные бизнес-данные, а не текст внутри `Job`, `Widget` или исходного кода.** F2 определяет их типизированные сущности, устойчивую identity, связи, версии, разрешённость и интерфейсы доступа; F3 предоставляет независимый persistence adapter, а конструкторы и публикация через Admin относятся к последующим этапам согласно плану.

- **Общие правила:** `Global Client Rules` и `Global Master Rules` принадлежат опубликованной конфигурации Helpy и применяются по роли, без копирования текста в каждую сущность.
- **Специфичные правила:** `Client Entity Rules` и `Master Entity Rules` принадлежат соответствующей сервисной сущности и, где это предусмотрено исходным Registry, конкретному сценарию. Информационные блоки могут адресоваться клиенту, мастеру или обеим ролям.
- **Переиспользование:** несколько категорий, сущностей или сценариев могут ссылаться на **один блок по стабильному ID и редакции**. Привязка ссылается на блок, не создаёт его копию; если одинаковый текст исторически дублируется, единое представление допустимо только при доказанном совпадении утверждённого смысла и области применения.
- **Сборка отображаемой информации:** для роли в контексте заказа определяется применимый набор общих и специфичных блоков, с проверкой их версии, видимости и принадлежности. Сами блоки показываются по действию **«Информация по заказу»** отдельно от структурированного ТЗ. Правила с обязательствами/ограничениями доступны до принятия соответствующего обязательства.
- **Управление информационными блоками:** создание, независимое редактирование языковых редакций, изменение порядка в применимом контексте, публикация, отключение, повторная публикация и удаление из действующего набора доступны уполномоченному Admin. Используются стабильные ID, версии и правила публикации §3.3. Изменение видимости/удаление не уничтожает историческую редакцию и не меняет зафиксированные обязательства.
- **Снимки и аудит:** публикуемый заказ сохраняет применённые идентификаторы/редакции бизнес-правил и согласованные условия. Историческая редакция остаётся доступной при проверке/урегулировании. Замена текста в текущей опубликованной конфигурации применяется к новым обязательствам, а не задним числом.
- **Содержание:** общие и специфичные Client/Master Rules читаются только по точным диапазонам §2.1. Сохранить утверждённый смысл и формулировки исходного содержания в применимых тестовых эталонах F2. Отсутствующие продуктовые переводы готовятся как кандидаты на Этапе 3 по §3.3; F2 не обязан переводить весь каталог. Не переносить код, схему или исторические инструкции. Профессиональный совет/информация не становится автоматически обязательным шагом UseCase. F2 создаёт и тестирует механизм на адресных эталонах и явно тестовых данных; фактическое наполнение и лингвистическая приёмка — Этап 3 (§10).

В F2 требуются валидаторы отсутствующих/неактивных ссылок, версий, ролей и принадлежности блоков, UseCase композиции применимой информации, операции управления блоками и тесты §8. Конкретная схема таблиц D1 или место хранения файлов не устанавливаются в F2.

### 3.3. Нормативная матрица локализации и перевода TH/RU/EN

| Компонент | Механизм |
|---|---|
| Интерфейс Mobile | Готовые ресурсы локализации |
| Интерфейс Admin | Готовые ресурсы локализации |
| Категории и сущности | Опубликованные языковые редакции |
| Динамические формы | Опубликованные языковые редакции |
| Правила и подсказки | Опубликованные языковые редакции |
| Переговорный чат | Динамический перевод |
| Рабочий чат | Динамический перевод |
| Системный чат Helpy | Динамический перевод |
| Помощь Admin при подготовке контента | Машинный перевод с ручным редактированием |

- **Локализованный контент:** единый объект со стабильной identity и отдельными редакциями TH/RU/EN. Требование охватывает все управляемые пользовательские тексты, в том числе названия, описания, вопросы, варианты ответов, фото-подсказки, информационные блоки и правила. Admin независимо редактирует и проверяет каждую редакцию; правка одной не перезаписывает остальные. Машинный перевод, если запрошен Admin, создаёт только предложение для ручной проверки, не меняет опубликованное содержание и не означает утверждения.
- **Публикация:** новая версия доступна пользователям только после наличия и явного утверждения уполномоченным Admin всех трёх обязательных языковых редакций этой версии (`th`, `ru`, `en`). Изменение конфигурации доступных локалей или их порядка не позволяет уменьшить этот обязательный набор для публикации; расширение архитектуры на другие языки не отменяет этот инвариант. Утверждение относится к конкретной неизменяемой версии текста и набору языковых редакций. Изменённая редакция требует повторного утверждения; неизменённые тексты можно подтвердить без переписывания. При изменении смысла Admin повторно проверяет эквивалентность всех трёх редакций; прежнее утверждение не считается подтверждением нового смысла. Изменение только порядка отображения не требует повторного перевода текста. Публикация согласованного набора атомарна; устаревшее подтверждение или конкурирующая правка не позволяют опубликовать непроверенную редакцию. Неполная/неутверждённая версия не заменяет текущую опубликованную. Admin проверяет эквивалентность условий, обязательств, запретов и исключений. Первичный смысловой эталон — утверждённое содержание Registry по §2.1. В F2 используются адресные предметные эталоны и явно тестовые языковые редакции для проверки механизма; тестовое утверждение не означает лингвистическое утверждение продуктового текста. На Этапе 3 отсутствующие продуктовые языковые тексты создаются как кандидаты, проверяются и утверждаются Admin до публикации. Обратный перевод — вспомогательная проверка, не доказательство эквивалентности. F2 не требует массового перевода или лингвистической приёмки первоначального наполнения.
- **История:** изменяемый контент не отменяет программные инварианты настоящего контракта. Изменение договорного смысла действует на новые обязательства; исторические snapshots и редакции сохраняются. Исправленная и утверждённая языковая редакция может использоваться для отображения старого заказа только при подтверждённом сохранении смысла; исходная договорная редакция остаётся доступной. Переупорядочивание, отключение и удаление из актуальной конфигурации не уничтожают историю.
- **Интерфейсы:** сохраняется принятая общая локализация F1; Mobile/Admin переключаются между TH/RU/EN без перезапуска и сетевого перевода готовых ресурсов. Опубликованный контент отображается на выбранном языке без повторного машинного перевода. Недоступность переводчика не блокирует интерфейс, каталог или формы.
- **Переписка:** переговорный, рабочий и официальный системный контексты используют единое ядро чата (§5, §11.3.1) и общий заменяемый контракт перевода. Оригинал не меняется; перевод — отдельное представление на выбранном языке, включая ранее загруженные сообщения при смене языка. Ошибка провайдера не подменяет оригинал и не меняет бизнес-состояние. Конкретный провайдер не фиксируется; его замена не изменяет опубликованные редакции. Помощь Admin использует тот же независимый контракт перевода, но отдельную операцию подготовки черновика с ручным утверждением.
- **Граница F2:** Domain/Application реализует типизированные локализованные редакции, права редактирования/утверждения, проверку публикации, версии, выбор локали, независимый переводческий порт, обработку результата/ошибки и соответствующие тесты. Без реального переводческого SDK, UI, persistence и фактического массового перевода. F3+ подключает адаптеры и UI по плану; начальное наполнение и языковая приёмка на Этапе 3.

## 4. Снимки заказа, мастер и цена

1. До публикации клиент вправе редактировать черновик. **После публикации заказ и его ТЗ не изменяются и не редактируются**: исходные структурированные данные, ответы, фотографии, CEP, версия каталога и правила образуют неизменяемый снимок. Admin не переписывает его. Новые обстоятельства отражаются только самостоятельными событиями переговоров/исполнения, а не редактированием опубликованного ТЗ. Для другого ТЗ клиент создаёт новый заказ с новым `job_id`.
2. Мастер самостоятельно выбирает всю категорию (включая новые опубликованные сущности) либо отдельные сущности (новые автоматически не добавляются). Специализация — **только фильтр ленты заказов**, а не подтверждение квалификации или разрешение на работу. При пустом выборе лента пуста. Заказы по времени публикации, новые сверху; **без языкового и географического фильтра, языкового приоритета или рейтинга**. Возможность будущего расширения правил показа по языкам предусматривается только как архитектурная заменяемость политики фильтрации; **в F2 и на запуске языковая фильтрация, сведения о владении языками, настройки и ранжирование по ним не реализуются**. Отдельное уведомление о языке оригинала сообщения во временном чате (§5, пункт 7) не зависит от фильтрации ленты.
3. До окончательного назначения мастера точный адрес и контакты клиента скрыты; переписка только через Helpy.
4. Клиент указывает ожидаемую цену. Мастер может её принять либо **один раз после обязательного обсуждения** предложить другую. Предупреждение не расходует попытку; попытка расходуется только успешной фиксацией предложения.
5. Клиент отдельно подтверждает согласованную цену и выбор мастера. **Выбор допускается только после отправки мастером окончательного предложения (`Final Application`) по действующей согласованной цене** (§4.1). На выборе фиксируются FAP, THB, выбранный мастер, ставка комиссии и финансовая policy/version. Это **резервирование**, не окончательное назначение.
6. После выбора мастера остальные предложения и переговоры закрыты; возврат этого job в marketplace для другого мастера запрещён.

### 4.1. Полный жизненный цикл Offer — восстановленное требование Registry

**Нормативная граница:** действующий жизненный цикл предложения полностью определяется настоящим §4.1 и связанными разделами единого F2. Для уточнения семантики исторических сущностей допускается чтение соответствующих фрагментов локального Registry по §2.1, но документы старой API/DB-реализации и прежние контракты не являются инструкциями исполнителю. Устаревшие депозит, отдельный рабочий чат, Safety Gate проверки квалификации и административное разрешение на повторное изменение цены **не переносить**.

1. **Публикация:** клиент задаёт собственную ожидаемую стоимость (`Client Expected Price`, CEP). Это исходная сумма заказа, **не** рекомендация Helpy и **не** будущая база комиссии. В опубликованном снимке зафиксированы CEP и исходное ТЗ.
2. **Первичный отклик:** мастер может подать предложение по опубликованному и доступному ему заказу в действующем периоде при соответствии выбранной им специализации. Отклик связывает `job_id`, конкретного мастера, редакцию ТЗ, заявленную исходную цену и временный `chat_id`; отклик сам по себе не доказывает двусторонних переговоров и не продлевает срок публикации.
3. **Без изменения цены:** если CEP подходит мастеру, он вправе отправить **окончательное предложение** (`Final Application`) с неизменённой CEP без фиктивного пересмотра. **Перед отправкой показывается подтверждение с суммой и получателем; окончательная заявка отправляется только после явного подтверждения мастера**. Простой просмотр, закрытие окна и отказ подтверждать ничего не отправляют. Final application не создаётся автоматически первичным откликом.
4. **С изменением цены:** только **после реального обсуждения с клиентом** мастер вправе **один раз** предложить другую сумму с объяснением причины. Перед записью показываются сумма, причина и явное подтверждение отправки; закрытие/отмена подтверждения **не расходует** попытку. Попытка расходуется только успешной записью ценового предложения. Клиент отдельно и явно подтверждает изменённую цену, прежде чем мастер сможет отправить final application с этой ценой. Отказ клиента не даёт мастеру второго изменения суммы.
5. **Окончательное предложение:** мастер **после отдельного подтверждения отправки** направляет `Final Application` с конкретной согласованной суммой, связанной с текущими `Offer`, `Job` и неизменяемым опубликованным ТЗ. `Final Application` ещё **не** назначает мастера, не создаёт платёж и не закрывает другие переговоры. В интерфейсе клиента оно доступно для последующего отдельного выбора исполнителя.
6. **Подтверждения клиента:** принятие другой цены (если мастер предложил её) и выбор исполнителя — **отдельные действия**. Перед выбором показываются мастер и окончательная сумма; выбор выполняется только после явного подтверждения клиента, а отмена подтверждения ничего не меняет. Выбор допускается исключительно для действительного, не закрытого final application данного мастера, без последующего изменения его суммы. В момент выбора формируется FAP и неизменяемый финансовый снимок; мастер резервируется, но assignment ждёт безналичной оплаты 100% FAP либо выбора доступного Cash (§6).
7. **Состояние и доказательства:** отдельный `Offer` хранит актуальное состояние и факты initial/revised/final price, причину и подтверждение пересмотра, отметку отправки final application; отдельные `JobEvent` фиксируют `initial_offer_sent`, `price_adjustment_requested`, `price_adjustment_approved`, `final_application_sent`, `master_selected`. Переписка даёт контекст, **но не заменяет** эти структурированные события. Дублирующее событие не должно повторно менять цену или выбирать исполнителя.
8. **Параллельные отклики:** до выбора клиента могут существовать независимые offers и временные чаты разных мастеров; предложение одного не даёт доступ к переписке другого. После выбора закрываются остальные offers и чаты, выбранный `chat_id` сохраняется в переходе к оплате и работе. Закрытый или исключённый из этого `job_id` мастер не получает новый отклик на тот же заказ через цикл повторной публикации.
9. **Завершение без выбора:** непринятое клиентом окончательное предложение действует лишь пока допускает жизненный цикл публикации/защищённых переговоров (§5, §11.1); по применимому тайм-ауту оно становится недействительным и исчезает из выбора без дисциплинарного отказа мастера. Закрытие окна чата крестиком не отменяет это предложение и не меняет таймер. Подтверждённое нажатие «Завершить переговоры» прекращает переговоры с конкретной парой и немедленно отменяет отправленную, ещё не принятую цену и `Final Application`; повторно принять их нельзя. Системный тайм-аут и явный отзыв — разные основания завершения. Final application не даёт права восстановить завершённый offer.

**Защита опубликованного ТЗ / запрет Job Revision.** По окончательному решению владельца **опубликованный заказ не изменяется и не редактируется**. В F2 не существует операции редактирования/перепубликации изменённого ТЗ, в том числе через Admin; старые offers нельзя переносить на новый объём работ. Редактирование разрешено только для `draft` до первоначальной публикации. Если клиенту нужно другое ТЗ, он создаёт отдельный заказ с новым `job_id`. Повторные публикационные циклы по §5 показывают **тот же неизменённый заказ**, не являются редакциями заказа. Никакого незакрытого вопроса о `JobRevision` для текущего запуска нет.

**Историческая граница:** старый Registry упоминает `minimum threshold` ожидаемой цены, исключение для повторного пересмотра через Admin и `Safety Gate`. Эти элементы **не подтверждены как новые правила запуска** последними решениями об упрощении посреднической площадки. Они здесь не вводятся. Комиссия от CEP не считается; только от FAP.

### 4.2. Учёт подтверждённых отказов мастера (`refusalStreak`) — решение владельца от 16.11.2026

**Назначение:** история подтверждённых добровольных отказов и адресованные предупреждения мастеру; это инструмент прозрачности и дисциплины, **не автоматический механизм блокировки, ограничения ленты, ранжирования или отказа в заказах**. Всякая автоматическая блокировка по числу отказов, включая старое правило «3 отказа → `suspended`», **отменена решением владельца**. Сам счётчик не меняет право мастера получать и принимать новые заказы.

**Отказ учитывается только по доказанному основанию:** (а) мастер явно отозвал уже отправленное и ещё действующее предложение/`Final Application` до выбора клиента, подтвердив отдельное предупреждение; (б) после назначения мастер добровольно отказался от выполнения конкретного заказа, и соответствующий структурированный `ResolutionDecision` подтвердил именно этот исход. В первом случае предложение становится терминальным, а мастер исключается из **этого `job_id`** на последующих публикационных циклах; это **локальное последствие отзыва конкретного предложения, не общая блокировка мастера**. Во втором случае применяются только утверждённые правила отмены/финансового исхода из §9.2.

**Не являются отказом:** просмотр заказа, отсутствие отклика, молчание, уход приложения в фон, закрытие окна чата крестиком, истечение срока публикации или одностороннего чата, непринятие клиентом предложения, завершение переговоров при отсутствии действующего отправленного предложения и запрос спорной отмены до решения Admin. Системное закрытие/истечение предложения, равно как отказ клиента, не превращается в добровольный отказ мастера.

**Разграничение операций и подтверждение:** крестик/навигация **только скрывают окно переписки**; `chat_id`, переговоры, действующее отправленное ценовое предложение и `Final Application` остаются в прежнем состоянии, клиент может принять действительное `Final Application` согласно §4.1 до его естественного завершения по срокам §5. Кнопка **«Завершить переговоры»** — отдельная терминальная операция для конкретной пары `job_id`/`master_id`: перед выполнением у обеих ролей запрашивается явное подтверждение, что переговоры будут завершены, а **предложенная мастером сумма и любое ещё не принятое клиентом `Final Application` будут отменены и исчезнут из доступного выбора**. Отмена подтверждения ничего не меняет. Для мастера, который ранее отправил действующее предложение, такое подтверждённое завершение одновременно является явным отзывом предложения и учитывается **ровно один раз** в `refusalStreak` по этому разделу; перед подтверждением мастер также видит предупреждение об учёте отказа и исключении из повторных циклов **этого `job_id`**. Если действующего отправленного предложения нет, `refusalStreak` не изменяется. Отдельное действие «Отозвать предложение», если оно доступно в интерфейсе, применяет ту же доменную операцию отзыва и не может создать второй отказ. Ранее выбранного/зарезервированного мастера эта операция не отменяет: после выбора действуют правила §6 и §9. Простое закрытие окна не означает завершение переговоров, отзыв суммы, отказ мастера или запуск нового цикла; окончательное предложение, не принятое клиентом, автоматически прекращает действие при применимом тайм-ауте жизненного цикла по §5, без дисциплинарного отказа.

**Учёт и предупреждения:** каждое новое подтверждённое основание увеличивает `refusalStreak` ровно на единицу; после первого события мастер получает нейтральное предупреждение об учёте отказа, после второго и последующих — предупреждение о повторяющихся отказах и необходимости соблюдать подтверждённые договорённости. **Запрещено обещать автоматическую блокировку при следующем отказе.** Количество отказов может быть доступно уполномоченному Admin для просмотра истории и индивидуального рассмотрения, но не создаёт самостоятельного решения об ограничении доступа. Регистрация отказа не меняет финансовых исходов и не создаёт штраф вне уже утверждённых правил §9.2.

`refusalStreak` сбрасывается **при единственном подтверждённом переходе заказа этого мастера в `completed`**: как при обычном закрытии мастером, так и при исключительном завершении через уполномоченный Admin согласно §9.3.1, если работа уже принята клиентом. Просмотр, отклик, резерв, оплата, назначение, завершение чата, одна лишь приёмка клиентом, истечение порога бездействия и административное чтение истории не сбрасывают счётчик. Исторические события отказов сохраняются в аудите независимо от сброса последовательного счётчика.

**Доменный контракт F2:** типизированное событие добровольного отказа с `master_id`, основанием, ссылкой на `job_id`/`offer_id` либо `ResolutionDecision`, временем и идентификатором операции; идемпотентный учёт и атомарное увеличение `refusalStreak`; событие адресованного предупреждения; сброс последовательности при `completed` без удаления истории. Повторная доставка, параллельные обращения и повторное решение одного основания не увеличивают счётчик повторно. Ни один UseCase eligibility, marketplace-feed или выбора мастера **не имеет права запрещать работу только по величине `refusalStreak`**. UI и доставка предупреждений относятся к последующим этапам.
## 5. Публикация, переговоры, единый чат

1. Первоначальная публикация: 24 часа по умолчанию, Admin может изменить или отключить автозакрытие для новых первых публикаций по §11.5, п. 5. После применимого дедлайна новые предложения закрыты.
2. **Нет откликов** либо были только предложения/односторонние сообщения без двусторонних переговоров → по окончании первого периода заказ закрыть, уведомить клиента; новый заказ потребует новый `job_id`. Никаких циклов 12/6/3 для такого случая.
3. Реальный обмен сообщениями **обеими сторонами** образует переговоры, которые нельзя прерывать из-за истечения текущего срока публикации. Несколько диалогов защищаются независимо. Одностороннее сообщение не образует защиту.
4. **Крестик/переход с экрана** закрывает только окно переписки и не влияет на действующие предложение, `Final Application`, защиту двустороннего чата и сроки. **«Завершить переговоры»** доступно клиенту и мастеру, требует отдельного подтверждения последствий и терминально закрывает переговоры конкретной пары **с отменой предложенной суммы и непринятого `Final Application`** (§4.2). При отзыве действующего отправленного предложения мастером учитывается один подтверждённый отказ; при отсутствии такого предложения отказ не начисляется. Молчание и закрытие окна не равны отказу и не завершают защищённый диалог.
5. Если в текущем цикле состоялись двусторонние переговоры, завершившиеся без выбора мастера, следующий цикл того же заказа запускается **после истечения текущего срока публикации** и завершения всех защищённых переговоров (в зависимости от того, какое из событий наступит позже): 12 → 6 → 3 → 3… часов (Admin-configurable). ТЗ, фотографии, исходная ожидаемая стоимость и `job_id` сохраняются. Пока защищённые переговоры есть, повторной публикации нет.
6. Напоминания только стороне без ответа: первое через час, затем каждый час до ответа либо завершения чата. Интервалы управляются Admin. Независимого 30-минутного TTL и таймера автоотказа от молчания нет.
7. **Единственная дополнительная языковая функция переговоров на запуске (помимо общей локализации и перевода по §3) — уведомление мастера о языке оригинального сообщения клиента во временном чате.** Язык определяется по фактически написанному тексту, **не** по языку интерфейса и **не** как подтверждение владения разговорным языком. Мастер продолжает видеть перевод сообщения на свой язык. Уведомление «Клиент пишет на … языке» появляется при определении языка и **остаётся видимым до первого ответа мастера**, в том числе после закрытия/повторного открытия приложения и независимо от времени ожидания; не повторяется при каждом сообщении с тем же языком. Если клиент меняет язык переписки, уведомление обновляется и снова остаётся до следующего ответа мастера. При недостоверном определении язык не угадывать. Уведомление **не ограничивает** показ заказов, отклики, доступ к чату или выбор исполнителя.
8. У выбранной пары **один `chat_id`** на переговоры → резервирование → оплату → рабочий режим → завершение. Новый рабочий чат не создавать; история сохраняется. Невыбранные чаты закрывать и уведомлять участников.
9. Временный режим: фото в сообщения отправлять нельзя, при этом фотографии из исходного ТЗ доступны для просмотра. После назначения и перехода в рабочий режим обе стороны могут отправлять **не более одной фотографии в сообщении** без общего ограничения количества. По закрытии заказа сообщения недопустимы, история сохранна.

### 5.1. Нормативная матрица публикации и временных переговоров

| Состояние/условие | Допустимый результат | Запреты и сохраняемые данные |
|---|---|---|
| `draft` → первая публикация | Один опубликованный snapshot, `job_id`, момент начала и зафиксированный deadline первого цикла (launch default — 24 ч), либо отсутствие автоматического deadline при отключённом автозакрытии | После публикации никакого редактирования ТЗ/CEP/фотографий, включая Admin |
| Первый цикл до deadline, мастера не выбрали | Приём новых откликов подходящих по специализации мастеров; независимые временные переговоры | Один чат не даёт доступа к другому; отклик или одностороннее сообщение сами по себе не защищают от deadline |
| Мастер и клиент реально обменялись сообщениями до deadline | Конкретный диалог получает состояние защищённых двусторонних переговоров | Нельзя приравнивать к этому событию лишь отклик, Final Application, просмотр чата или одностороннее сообщение |
| Deadline наступил, защищённых переговоров нет и их не было | Первый цикл завершается, заказ закрывается, клиент уведомляется | Не запускать повторные циклы; поздний отклик не принимать |
| Deadline наступил, один или несколько защищённых диалогов продолжаются | Новые отклики больше не принимаются, существующие защищённые переговоры продолжаются | Нельзя автоматически закрывать защищённый чат по deadline, назначать отказ по молчанию либо начинать новый цикл параллельно |
| Клиент/мастер нажал «×»/закрыл окно чата | Скрыть окно без доменного перехода; сохранить чат, действующее предложение и Final Application для принятия клиентом до применимого timeout | Не завершать переговоры, не сбрасывать `refusalStreak`, не изменять срок публикации или защищённость |
| Клиент/мастер подтвердил «Завершить переговоры» | Терминально закрыть только соответствующие переговоры `job_id` + `master_id`/`chat_id`; отменить предложенную цену и непринятое Final Application, исключив их из выбора | Отдельное предупреждение о потере предложенной стоимости обязательно; если мастер отзывает собственное действующее предложение, один отказ по §4.2; без действующего предложения отказа нет; другие пары и действующий срок публикации не затрагивать |
| До выбора мастера уполномоченный Admin после рассмотрения обстоятельств принимает явное решение закрыть конкретный открытый переговорный чат | Закрыть только соответствующие переговоры с сохранением истории и audit решения; непринятая цена/Final Application больше не доступны для выбора; применить общие условия следующего цикла §5.1 | Не продлевать или перезапускать таймер, не закрывать другие пары, не начислять добровольный отказ мастера только из факта административного закрытия; не подменять Payment/Resolution; после выбора мастера эта операция недопустима |
| Deadline публикации наступил, а конкретный временный чат остался односторонним | Закрыть такой незащищённый временный чат и связанное предложение как истёкшие без выбора мастера | Это не отказ мастера; не затрагивать иные защищённые двусторонние переговоры, если они продолжаются |
| Все защищённые переговоры безрезультатно завершены **после deadline** | Следующий цикл того же заказа: первоначальный 24 ч → 12 ч → 6 ч → 3 ч → последующие по 3 ч | Не менять `job_id`, snapshot, CEP, фотографии, историю; ранее исключённому мастеру не разрешать новое предложение по этому `job_id` |
| Все двусторонние переговоры текущего цикла завершены без выбора **до deadline** | До deadline продолжать текущую публикацию; если к его наступлению мастер не выбран и нет иных защищённых переговоров, запустить **следующий повторный цикл** (после первого — 12 ч; далее 6/3/3… ч) | Не закрывать заказ как «пустой»: двусторонний обмен в этом цикле уже состоялся; не запускать следующий цикл досрочно |
| **Повторный** цикл достиг deadline, но в течение этого цикла **не возникло новых двусторонних переговоров** | **Закрыть заказ окончательно** и уведомить клиента (утверждён вариант B) | Не запускать следующий цикл; прошлые переговоры не продлевают пустой повторный цикл; односторонние сообщения не создают защиту |
| Клиент выбрал мастера и подтвердил выбор | Закрыть все прочие предложения/временные чаты; выбранный `chat_id` переходит к резервированию | Не запускать следующие циклы, не возвращать заказ в ленту; дальнейшие таймеры регулирует §6 |
| Сторона ожидает ответа в открытом временном чате | Напомнить ожидаемой стороне через 1 ч, далее каждый час до ответа/закрытия; значения из Admin policy | Напоминание не является отказом/ответом/продлением срока; никаких отдельных 30-минутных TTL |

**Настройка через Admin:** отдельно задаются начальный период, последовательность последующих периодов и минимальный повторяемый период, а также интервалы первого/повторного напоминания. Значения 24/12/6/3 ч и 1/1 ч — первоначальные значения конфигурации, не константы в бизнес-алгоритмах. Возможность отключить автоматическое закрытие первой публикации сохранена: состояние автозакрытия фиксируется при начале первой публикации по §11.5, п. 5; если оно отключено, у этого цикла нет автоматического deadline-триггера. Последующее включение или отключение автозакрытия применяется только к новым первым публикациям; повторные циклы регулируются собственной policy. Admin не продлевает жизненный цикл чата вручную: сроки и напоминания отрабатываются автоматически, административное вмешательство ограничено явным решением о закрытии чата по указанному в матрице основанию. Отдельной операции продления, настройки продления или дополнительного таймера не вводить. Временные расчёты выполняются доменным `Clock`, переходы — атомарно и идемпотентно относительно одного и того же события deadline/закрытия/выбора.

**Утверждённый досрочный исход (вариант A, 16.11.2026):** если двусторонние переговоры состоялись в текущем цикле и завершились без выбора мастера ещё до его deadline, публикация продолжается до deadline. По его достижении, если мастер не выбран и нет других действующих защищённых переговоров, начинается следующий цикл 12 → 6 → 3 → 3… ч. Например, переговоры в первоначальных 24 часах закончились через 5 часов: оставшиеся 19 часов заказ остаётся опубликованным; затем начинается 12-часовой цикл. Ранее состоявшиеся переговоры **не считаются новыми переговорами следующего цикла**: если новый повторный цикл пуст, он закрывает заказ на своём deadline (вариант B).

**Вариант B (пустой повторный цикл):** нормативный переход и его условия заданы строкой матрицы §5.1 «Повторный цикл достиг deadline, но новых двусторонних переговоров нет». После терминального закрытия нельзя создать новые offers, переговорные чаты или очередной публикационный цикл. Закрытие и обработка deadline идемпотентны; правило первоначального периода не меняется.

## 6. Payment Reservation: один перезапускаемый счётчик оплаты

1. После резервирования выбранного мастера действует `paymentSelectionTimeout = 600 с` по умолчанию, Admin-configurable. Клиент должен успеть инициировать допустимую безналичную операцию либо выбрать разрешённый Cash.
2. **Своевременно начатая** платёжная операция не отменяется из-за позднего ответа внешнего провайдера. У провайдера отдельное состояние/политика подтверждения, не 600-секундный клиентский таймер. Повторные и запоздалые события — идемпотентно, без двойного назначения и платежа.
3. При **первом достоверном окончательном** `PaymentOperation=failed` **сбросить и повторно запустить тот же счётчик времени оплаты** на полную длительность `paymentSelectionTimeout` (по умолчанию 600 с). **Второго окна и отдельного `paymentRetryWindow` нет.** Повторные ошибки в пределах обновлённого срока не перезапускают счётчик вновь; каждая платёжная попытка имеет отдельный идентификатор и историю. После подтверждённого failed можно выбрать другой разрешённый безналичный способ либо доступный Cash. Длительность счётчика задаётся в Admin и не хардкодится; правило единственного сброса закреплено для этого lifecycle.
4. Выбранный мастер, FAP, financial snapshot и тот же чат сохраняются в ходе повтора; иные offers не восстанавливаются.
5. Cash допустим только при включённой Admin policy и когда **текущий долг мастера ниже его персонального порога**. Клиент **до выбора мастера** видит, что при достижении порога этот мастер работает **только с безналичной оплатой**; Cash отсутствует среди вариантов оплаты для этой пары. Домен повторно проверяет доступность Cash при выборе метода и назначении. Достижение порога не скрывает мастера и не исключает его из ленты, не блокирует noncash. Смена метода оплаты не меняет FAP.
6. Подтверждённая безналичная оплата **100% FAP** или разрешённый Cash дают окончательное назначение мастера и рабочий режим **того же чата**. Депозита нет. При Cash деньги передаются мастеру напрямую.
7. Если первоначальный срок истёк **без своевременно инициированной операции/Cash**, либо срок после единственного сброса закончился **без успешного результата/Cash и без неразрешённых операций провайдера**, либо клиент явно отказался до назначения **при отсутствии неразрешённых финансовых операций**, наступает терминальный исход: резерв снят, мастер освобождён, чат закрыт; старый заказ **не возвращается в ленту и не реактивируется**, новый заказ — с новым `job_id`. Это не отказ мастера. **Если операция ещё `pending/unknown`, одного истечения клиентского окна недостаточно для освобождения резерва:** применяются §6.3 и §11.2.
8. Пока текущая операция имеет `pending/unknown`, **запрещены выбор Cash, переключение способа оплаты и запуск второй платёжной операции**. Действия разблокируются только после достоверного терминального исхода, если сохраняется срок и право на повтор; после `success` мастер уже назначен, и повтор невозможен. Неопределённые ответы провайдера нельзя приравнивать к `failed`; конфликт с дедлайном разрешается без двойного списания и назначения.

### 6.1. Отображение обратного отсчёта клиенту (обязательный контракт UI)

1. После подтверждённого выбора мастера клиент **сразу видит на экране оплаты обратный отсчёт оставшегося времени** резервирования мастера, а также понятное указание, что для сохранения заказа необходимо вовремя выбрать Cash либо начать безналичную оплату. Таймер нельзя прятать в меню или показывать только в уведомлении.
2. Значение отсчёта вычисляется из сохранённого доменного deadline и текущего времени, а не из локального количества тиков Flutter. После ухода с экрана, повторного открытия приложения или смены устройства отображается действительный остаток, а не новый полный интервал.
3. После **первой подтверждённой ошибки** тот же видимый счётчик обновляется на полную Admin-настраиваемую длительность. Последующие ошибки его не сбрасывают. Приложение явно сообщает клиенту, что предыдущая оплата не удалась и доступна повторная попытка до показанного срока.
4. **Причина достоверного отказа платёжного провайдера показывается клиенту непосредственно на экране оплаты**: например, `insufficient_funds` отображается как «Недостаточно средств» на выбранном языке TH/RU/EN. Для остальных известных кодов отказа используется безопасное понятное описание, соответствующее фактическому ответу провайдера; необработанный технический код, персональные платёжные реквизиты и внутренние диагностические сведения пользователю не показываются. Если провайдер не сообщил причину, показывается нейтральное «Оплата не выполнена» без выдуманного объяснения. Сообщение об отказе не подменяет состояние `pending/unknown` и не открывает повтор до достоверного terminal `failed`. В F2 определяются типизированный код/категория причины и безопасный контракт отображения, а провайдерский адаптер и локализованный UI реализуются позднее.
5. Пока операция `pending/unknown`, интерфейс показывает **«Ожидаем подтверждения оплаты»** и блокирует Cash, смену способа и новую попытку. Если клиентский deadline истёк во время такого ожидания, нельзя показывать, будто резерв автоматически снят или заказ отменён: состояние ожидания провайдера сохраняется по §6.3.
6. После подтверждённого `success` или выбора допустимого Cash отсчёт прекращается и интерфейс показывает назначение мастера. Если срок действительно истёк без активной операции и без Cash, показывается понятное сообщение о завершении резервирования; заказ не возвращается в ленту.
7. F2 предоставляет точный deadline и состояние оплаты через доменную модель/UseCase. Визуальный счётчик, предупреждение, локализация TH/RU/EN и обновление экрана реализуются на этапе Mobile. Длительность берётся из Admin policy, **без хардкода 600 секунд в UI**.

### 6.3. Утверждённая блокировка параллельных способов оплаты

**Решение владельца (16.11.2026):** переключение на Cash или другой безналичный способ и новая платёжная попытка возможны **только при достоверном исходе предыдущей операции**. При `pending/unknown` любые альтернативные маршруты и повторная инициация платежа заблокированы, даже если истёк клиентский таймер; резерв сохраняется до разрешения исхода провайдером. При `success` мастер немедленно назначается, и другие платежи запрещены. После `failed` право на повтор определяется оставшимся временем единожды обновлённого счётчика (§6), а не появлением второго окна. Все операции имеют уникальные идентификаторы и идемпотентную обработку событий.

## 7. Комиссия и долг мастера

1. Комиссия по умолчанию 30% FAP, изменяется через Admin и фиксируется в financial snapshot. Noncash: после подтверждённой оплаты платформа учитывает расчётную долю мастера после комиссии.
2. После **успешного завершения Cash-заказа** возникает комиссия-задолженность мастера перед Helpy в размере `FAP × snapshottedCommissionRate`; сама оплата FAP происходит напрямую между клиентом и мастером, средства клиента Helpy не получает. **Порог задолженности — Admin policy с индивидуальным значением для каждого мастера**, например 1000 THB у одного и 3000 THB у другого; глобальный launch default не является жёстким пределом 1000–2000 THB. При `outstandingDebt >= effectiveMasterDebtThreshold` клиенту до выбора мастера показывается режим **«Только безналичный расчёт»**, Cash не предлагается и запрещён доменной проверкой. Долг не мешает получать отклики и выполнять безналичные заказы.
3. **Автоматическое погашение задолженности при штатной безналичной выплате** выполняется исключительно по формуле §7.3 с фиксированной утверждённой ставкой 70% от суммы после комиссии и ограничением фактическим остатком долга. Ставка и формула удержания не являются Admin policy: глобальное и индивидуальное изменение, override и ручной пересчёт запрещены. `MasterPayout` рассчитывается после `completed` по актуальному учётному остатку долга; повторное перечисление использует неизменяемый расчёт. Добровольное погашение по §7.0.1 — отдельный механизм, не изменяющий формулу удержания.
4. **На главном экране мастера постоянно виден отдельный элемент «Задолженность» — не спрятанный в меню.** Нажатие на него открывает информацию о текущей задолженности перед Helpy и **действующем пороге именно этого мастера** в формате «300 из 1000 THB» (`outstandingDebt` из `effectiveMasterDebtThreshold`). При индивидуальном Admin-пороге, например 3000 THB, отображается именно он, а не глобальное значение. Информация доступна и при нулевом долге («0 из 1000 THB»); при достижении порога мастер видит, что Cash недоступен до снижения задолженности ниже порога. Здесь же доступно действие «Погасить долг» с вводом суммы и отправкой заявки Admin по §7.0.1. Добровольное погашение уменьшает задолженность **лишь после подтверждения фактического получения средств администратором**. Доменные данные о долге и пороге предоставляет F2; постоянно видимый элемент главного экрана мастера и экран детализации реализуются на соответствующем UI-этапе.

### 7.0.1. Добровольное погашение задолженности по заявке мастера — утверждённый пользовательский сценарий

1. **Точка входа мастера.** На главном экране мастера постоянно отображается отдельный элемент **«Задолженность»**. При открытии мастер видит **фактическую текущую задолженность** и **действующий именно для него максимальный порог**, например «300 из 1000 THB», а также пояснение: **при достижении порога Cash-заказы недоступны, остаются заказы только с безналичной оплатой**. Если задолженность меньше порога, Cash допускается по прочим действующим правилам. Никакой запрет на безналичные заказы из задолженности не следует.
2. **Инициирование заявки.** В окне задолженности находится кнопка **«Погасить долг»**. Мастер нажимает её, вводит желаемую сумму погашения **целыми THB** и подтверждает отправку запроса. Разрешено запросить погашение части задолженности либо всей задолженности; сумма должна быть положительной и не превышать фактический остаток долга на момент подачи. При нулевой задолженности заявку с положительной суммой создать нельзя. Сумма запроса фиксируется в его записи и не является фактом получения денег.
3. **Передача Admin.** После подтверждения создаётся адресованная Admin **заявка мастера на добровольное погашение** с уникальным идентификатором, `master_id`, суммой THB, временем и статусом, а также событие для уведомления Admin. Мастер видит, что запрос отправлен и ожидает рассмотрения. Отправка/повторная доставка сообщения не меняет баланс задолженности; повтор команды с тем же идентификатором не создаёт вторую заявку.
4. **Контакт и способ расчёта.** Admin получает заявку и **инициирует официальный чат поддержки Helpy с мастером**, привязанный к этой заявке (§11.3.1), чтобы согласовать, как площадка получит указанную сумму: **ровно одним из двух способов: наличными либо безналичным переводом от мастера на счёт Helpy**. Выбор способа и фактическая передача средств происходят по согласованию сторон. Погашение через согласованный индивидуальный процент удержания, отработку одного или нескольких заказов либо изменение штатной формулы не предусмотрено. Это **не** самостоятельная оплата встроенным клиентским `PaymentOperation` и не автоматическое подтверждение перечисления. F2 хранит бизнес-факты заявки, согласованного способа, подтверждения, ссылку на официальный диалог и audit; реализация интерфейсов переписки, доставки и внешнего перевода — последующие этапы. Само сообщение поддержки не является финансовым подтверждением: Admin отдельно проводит в панели операцию погашения по конкретному мастеру и заявке (§7.0.1, п. 5).
5. **Ручная операция Admin после получения средств.** После согласования и фактического получения суммы наличными либо безналичным переводом **уполномоченный Admin открывает в панели администратора задолженность конкретного мастера и явно выполняет операцию подтверждения погашения на полученную сумму**, с привязкой к заявке. Это не автоматическое списание и не действие, выполняемое из текста чата. Только по этой авторизованной команде система **атомарно** записывает единственный подтверждённый финансовый факт в `MasterDebt`/ledger, уменьшает задолженность указанного мастера и фиксирует сотрудника, время, основание, сумму и способ получения денег. Факт получения не должен выводиться из статуса «отправлено», переписки или сообщения мастера. Повторное подтверждение той же заявки не уменьшает долг повторно.
6. **Актуализация и конкурентные изменения.** На этапе подтверждения серверная доменная операция повторно сверяет текущий долг, уже подтверждённые поступления и удержания из выплат. Система не должна молча списывать больше текущего остатка или автоматически заменять согласованную сумму. При несовпадении с доступным долгом Admin требуется явное согласование корректной суммы **до проведения** финансового факта. Не подтверждённая заявка не резервирует долг и не освобождает Cash. После подтверждённого уменьшения долга видимая сумма обновляется, а право на Cash пересчитывается по действующему индивидуальному/глобальному порогу **для будущих решений о способе оплаты**, без изменения уже зафиксированных заказов.
7. **Отказ и недоказанное поступление.** Пока поступление не подтверждено, заявка остаётся незавершённой либо закрывается без финансового эффекта с основанием; при споре/неопределённости нельзя уменьшать долг предположительно. Все изменения заявки и баланса доступны для audit с проверкой роли. UI-кнопка, форма ввода, Admin Inbox и средства связи относятся к соответствующим этапам Presentation/Admin, но **доменная модель заявки, порт доступа, typed Failures, UseCases и тесты обязательны в F2**.

### 7.1. Целостность финансовых операций — обязательные доменные инварианты

1. **Единая денежная единица и точность.** Все пользовательские цены, платежи, комиссии, задолженности и выплаты запуска выражаются и отображаются **целыми THB, без десятичной запятой и дробной части**. Доменная модель хранит валюту `THB` явно и использует точную целочисленную денежную арифметику; двоичные вычисления с плавающей точкой для денег запрещены. Процентные формулы могут давать дробный промежуточный результат; он приводится к целому THB по утверждённому правилу математического округления (§7.2).
2. **Финансовая неизменяемость.** Для конкретного заказа при выборе мастера сохраняются `FAP`, валюта, применимая комиссия и версия финансовой политики. Изменение Admin-настроек впоследствии не пересчитывает уже зафиксированные условия. Персональный порог задолженности влияет на будущую доступность Cash, но не переписывает прежние расчёты.
3. **Однократная комиссия и долг.** Нормальное завершение Cash-заказа формирует ровно одно обязательство комиссии для пары `(job_id, commission_obligation_type)`. Повторный запрос завершения, повторное событие или повторный запуск обработчика не создают второго обязательства. Отмена Cash-заказа не создаёт долг, если по утверждённой финансовой политике комиссия не начисляется.
4. **Однократное погашение.** Каждая подтверждённая часть погашения задолженности имеет собственный уникальный финансовый факт и ссылку на основание (выплата по конкретному заказу либо подтверждённое Admin добровольное поступление). Повтор того же основания не уменьшает баланс ещё раз. Баланс долга не может стать отрицательным; удержание не превышает ни остаток долга, ни рассчитанный допустимый объём текущей выплаты.
5. **Устойчивость к событиям провайдера.** Каждая `PaymentOperation` и каждая операция `MasterPayout` имеют уникальную идентичность. Повторные, задержанные и переставленные по времени события проверяются по этой идентичности, сумме, валюте и допустимому переходу состояния. Дубликат подтверждения оплаты не назначает мастера второй раз и не записывает повторное поступление; дубликат подтверждения выплаты не повторяет её и не погашает долг снова. Противоречивые сообщения провайдера не интерпретируются как разрешение на новый перевод денег.
6. **Атомарность учёта.** Изменение финансового состояния и запись соответствующего неизменяемого события должны иметь одну согласованную границу фиксации. При ошибке записи не допускается частично проведённое начисление или списание. Безопасность повторной доставки событий должна поддерживаться постоянными идентификаторами, а не только памятью процесса.
7. **Независимый payout.** После `completed` сумма к выплате рассчитывается один раз из зафиксированных фактов и учтённого долга; применяется фиксированная формула §7.3; исходные суммы, остаток долга и результат фиксируются при создании расчёта. Повторная обработка payout не создаёт новую выплату на ту же причитающуюся сумму и не пересчитывает удержание. При ошибке payout заказ сохраняет `completed`, финансовое требование остаётся учтённым и может пройти контролируемый retry/manual resolution по исходным суммам; статус ошибки не считается подтверждением выплаты.
8. **Проверяемость расчёта.** Для каждого начисления, удержания, возврата и выплаты сохраняются исходные суммы, применённые ставки/версии, итоговые доли, идентификатор основания и audit-события. Проверка суммы распределённых долей должна выявлять расхождение, а не скрыто исправлять его произвольной дополнительной комиссией. Нулевая расчётная доля фиксируется как результат действующей формулы, но не создаёт внешнего перечисления, не требует платёжного маршрута и не считается подтверждённой отправкой денег; это правило не изменяет расчёт, бизнес-исход или другие ненулевые доли.

### 7.2. Целые THB и математическое округление — утверждено

**Денежные итоги выражаются только целыми THB.** Для расчёта процентных сумм используется математическое округление до ближайшего целого бата: дробная часть меньше 0,5 THB округляется вниз (остаток остаётся мастеру), дробная часть больше либо равна 0,5 THB округляется вверх (в пользу Helpy при вычислении её комиссии или долга). Граничное значение **ровно 0,5 THB округляется вверх**, по обычному правилу `half up`.

Примеры для комиссии Helpy 30%: `101 × 30% = 30,3 → 30 THB` комиссии и `71 THB` мастеру; `102 × 30% = 30,6 → 31 THB` комиссии и `71 THB` мастеру; `105 × 30% = 31,5 → 32 THB` комиссии и `73 THB` мастеру. Сумма долей всегда равна FAP. Для обязательств, удержаний и распределений сумма рассчитывается на основе точных рациональных ставок без ошибок binary floating point. Округление применяется к итоговому денежному обязательству один раз, а остаточная доля вычисляется вычитанием из исходной целой суммы, чтобы исключить расхождения. При распределении между несколькими получателями действуют проверяемые инварианты сохранения всей суммы; не допускается независимое округление, нарушающее баланс.

### 7.3. Единственная формула автоматического удержания и выплаты — действующие финансовые инварианты

1. **Два разных расчётных момента:** при подтверждённом выборе мастера `FinancialSnapshot` закрепляет `FAP`, валюту, комиссию и ставки отмены данного заказа. При создании `MasterPayout` после `completed` берутся ранее зафиксированные условия заказа и актуальный доступный остаток задолженности. Ставка автоматического удержания фиксирована нормативно: 70%, без глобальной или индивидуальной Admin-настройки.
2. **Начальный расчёт неизменяем:** `netBeforeDebt = FAP − snapshottedCommission`; `debtRecovery = min(actualOutstandingDebt, roundHalfUp(netBeforeDebt × 70%))`; `masterPayout = netBeforeDebt − debtRecovery`. Все суммы выражены целыми THB. Источником применённого остатка долга является актуальная учётная запись задолженности в атомарной операции создания расчёта, а не устаревшее значение в UI.
3. **Неизменяемость и права Admin:** Admin не вправе изменять ставку или формулу автоматического удержания, устанавливать индивидуальный коэффициент либо корректировать рассчитанную сумму выплаты. Повтор/ошибка перечисления не меняет созданный расчёт. Новая самостоятельная выплата использует ту же формулу и актуальный долг, с собственной зафиксированной комиссией заказа. Подтверждённое добровольное поступление влияет только на учётный остаток долга по §7.0.1.
4. **Несколько выплат и погашений:** конкурентные расчёты и подтверждённые добровольные поступления должны атомарно учитывать доступный остаток долга и исключать двойное резервирование/уменьшение одной суммы. После `completed` безналичного заказа, при подтверждённом наличии у Helpy средств для расчёта, погашение долга фиксируется однократно в финансовом учёте при создании расчёта выплаты: долг уменьшается на рассчитанное удержание, а оставшаяся сумма становится обязательством Helpy перед мастером. Результат отдельного исходящего перевода мастеру не отменяет такое погашение. Если исходящий перевод достоверно завершился `failed` и деньги не отправлены, повторяется **только перечисление оставшейся суммы по прежнему расчёту**, без нового удержания или пересчёта выплаты. При `pending/unknown` повторное перечисление запрещено до достоверного разрешения исхода, чтобы не отправить сумму дважды. Повторные callback и конкурентные операции не создают второго финансового эффекта.
5. **Разграничение механизмов:** глобальный/индивидуальный Admin-порог влияет только на доступность Cash при последующей проверке и не изменяет формулу или созданный payout. Заявка на добровольное погашение не изменяет процент автоматического удержания; фактическое подтверждённое поступление наличными либо переводом изменяет только остаток долга по §7.0.1.
6. **Проверка на примере:** `FAP=1000 THB`, комиссия из snapshot `30%` → `netBeforeDebt=700 THB`. При долге `300 THB` фиксированная ставка `70%` даёт удержание `300 THB` и выплату `400 THB`. При долге `1000 THB` удержание составляет `490 THB`, выплата `210 THB`, остаток долга `510 THB`. Ни Admin-настройка порога, ни попытка передать иной процент не меняют формулу или существующий расчёт.

Отсутствие экранов и виджетов не считается FAIL F2; UI-проверки сохраняются для соответствующего следующего этапа.

## 9. Восстановленный доменный контракт выполнения и завершения работ

**Действующее правило F2:** рабочая стадия продолжает заказной диалог той же пары с неизменным `chat_id`; при назначении изменяется состояние чата, новый диалог не создаётся. Требования этого раздела являются нормативными непосредственно в данном контракте.

### 9.1. Рабочая стадия и приёмка

1. Assignment наступает после подтверждённой полной non-cash оплаты FAP либо выбора допустимого Cash. Доступ к адресу клиента открывается назначенному мастеру **после assignment**, не при резервировании. Рабочий чат не имеет обычного TTL. Дополнительный обязательный `work_started`/`arrival_coordination` не вводится: время прибытия стороны согласуют в том же чате.
2. Мастер предоставляет результат/пояснения/фотографии как evidence. Наличие evidence **не обязательно** для приёмки клиентом: клиент может принять работу непосредственно на объекте. Клиент вправе отклонить результат с объяснением; мастер вправе исправить и повторно представить результат без отдельного лимита итераций. Принятие и отклонение результата доступны после assignment в допустимой рабочей стадии (`assigned/working`) без обязательного отдельного перехода `work_started` и без обязательной предварительной отправки evidence; при действующем CancellationRequest учитываются ограничения §9.2 и §9.3.1.
3. Нормальное завершение **двухступенчатое**: `client_accepts_work` фиксирует `completion_confirmed_by_client`, затем мастер выполняет `master_confirms_completion`; только после второго действия заказ получает `completed`. До этого штатная выплата noncash мастеру по завершённому заказу не становится доступной; это ограничение не распространяется на отдельную утверждённую компенсацию при terminal cancellation/Resolution по §9.2. После `completed` рабочий чат read-only, история сохраняется, клиенту доступна отдельная форма отзыва; streak отказов мастера сбрасывается.
4. Закрытие рабочего чата либо молчание стороны **не отменяет** назначенный заказ. После assignment прекращение происходит исключительно через структурированный Cancellation / Resolution. **После `client_accepted` обычная отмена заказа запрещена:** клиент уже подтвердил приёмку; исключительные обстоятельства рассматриваются через существующий `Resolution` с сохранением подтверждения приёмки и истории. Само обращение не меняет `client_accepted`, не разрешает отмену и не запускает денежный исход. Пока не доказаны условия ранее утверждённого исключительного завершения §9.3.1, дело остаётся в `admin_resolution_pending` без terminal decision; при отсутствии применимого утверждённого исхода Admin не выбирает произвольный refund, cancellation или payout. После нормального `completed` произвольный перевод в обычный dispute-flow не предусмотрен.

### 9.2. Cancellation / Resolution

1. Клиент после assignment **до `client_accepted`** может подать `CancellationRequest`, предварительно явно подтвердив предупреждение о финансовых последствиях. В запросе: структурированная причина, текстовое объяснение, необязательные evidence/photos. Normal completion приостанавливается до resolution.
2. Мастер разделяет согласие с прекращением работ и согласие с денежными условиями. Если финансовые условия оспорены, обязательны причина и объяснение; case переходит в `admin_resolution_pending`. Мастер также вправе сам инициировать отмену после предупреждения, с reason/explanation/evidence; доказанный добровольный отказ мастера влечёт полный возврат held noncash средств клиенту и увеличение refusal streak. **Утверждённый пограничный случай:** если инициированная мастером отмена не является доказанным добровольным отказом и не подпадает под уже утверждённые False Call или partial-work outcomes, запрос направляется в существующий `admin_resolution_pending` для проверки обстоятельств. Сам факт подачи такого запроса **не** начисляет штраф, комиссию за отмену, не увеличивает refusal streak и не вызывает автоматический refund/payout. До обоснованного решения Admin noncash средства остаются `held`; Admin не получает права изобретать новую ставку или финансовый исход. Для Cash Helpy не создаёт фиктивные денежные операции. Событие, основание и результаты проверки фиксируются в audit.
3. Для cancellation, требующей ответа второй стороны, `cancellationResponseTimeout=8 часов` и `cancellationReminderInterval=30 минут` — launch defaults, конфигурируемые через Admin. Молчание не означает согласие; по истечении запроса без ответа дело уходит Admin, noncash остаются held. Эти таймеры **не заменяют** правила переговоров и не применяются к специальному fixed False Call outcome.
4. Для noncash при обоюдной отмене по инициативе клиента **до прибытия мастера и без partial work** применяется `mutualCancellationFeeRate=15% FAP` по умолчанию: возврат 85% клиенту, 15% Helpy, 0 мастеру. Параметр конфигурируем и фиксируется в financial snapshot.
5. `False Call` после фактического прибытия мастера — структурированный cancellation outcome, а не новый процесс `claimed/confirmed`. Мастер указывает причину/описание и прилагает photo evidence. Для noncash действуют начальные Admin-configurable ставки `falseCallFeeRate=30% FAP` и `falseCallMasterShareRate=50% False Call Fee`. **Обе ставки и их версии берутся только из `FinancialSnapshot`, созданного при выборе мастера.** Расчёт в целых THB: `falseCallFee = roundHalfUp(FAP × snapshottedFalseCallFeeRate)`; `helpyShare = roundHalfUp(falseCallFee × (1 − snapshottedFalseCallMasterShareRate))`; `masterCompensation = falseCallFee − helpyShare`; `clientRefund = FAP − falseCallFee`. Расчёт доли Helpy первым и остатка мастеру обеспечивает утверждённое преимущество Helpy при округлении ровно 0,5 THB; сумму fee нельзя округлять повторно и нельзя независимо округлять обе доли. **Пример только для начальных ставок:** при FAP 1000 THB клиенту возвращается 700 THB, мастеру причитается 150 THB, Helpy — 150 THB; если fee равна 31 THB при ставке доли мастера 50%, Helpy получает 16 THB, мастер 15 THB. Любая изменённая Admin ставка применяется только к новым финансовым снимкам; в уже выбранном заказе она не меняет сумму. Общая сумма возврата и долей точно равна FAP. Дополнительная стандартная комиссия поверх False Call Fee **не начисляется**.
6. Если спор касается частично выполненной работы, фиксированные формулы mutual cancellation и False Call **не применяются**. Мастер передаёт reason, explanation, evidence и `remaining_work_description`; клиент может представить свою позицию и evidence. До решения Admin noncash held. Admin распределяет только `settlementPool = heldAmount − snapshottedCommission`, где `snapshottedCommission = roundHalfUp(FAP × snapshottedCommissionRate)` по единому правилу §7.2, между возвратом клиенту и компенсацией мастеру; сумма двух целых долей равна `settlementPool`. Доли определяются однократно с вычислением остатка вычитанием; комиссия не округляется повторно. Решение структурировано, обосновано, привязано к evidence и audit.
7. Для Cash Helpy не держит деньги клиента, не начисляет платформенные cancellation/False Call fee и не создаёт фиктивные platform refund/client debt. Личные расчёты сторон не моделируются Helpy; сохраняются только структурированные события, evidence и история.

### 9.2.1. Исполнение решения Admin — защита уже утверждённых финансовых исходов

1. `ResolutionCase` ссылается на конкретный `job_id`, исходный `CancellationRequest` (когда он есть), действующий `FinancialSnapshot`, доказательства и историю сообщений/событий. Admin получает доступ к необходимой для дела информации в пределах своей роли; просмотр evidence не меняет содержание заказа или исходную переписку. Информация о действиях Admin сохраняется в audit.
2. `ResolutionDecision` содержит конкретный тип ранее утверждённого исхода (согласованная отмена, признанный отказ мастера, False Call, частичная работа или исключительное завершение уже принятого клиентом заказа), основание, автора решения, время и точные целые суммы THB, когда по этому исходу предусмотрены денежные операции. **Это классификация уже согласованных исходов, а не разрешение Admin изобретать новые штрафы, ставки либо способы расчёта.** Для отмены, инициированной мастером по причине, не классифицируемой как доказанный добровольный отказ, False Call или partial work, Admin рассматривает обоснование и evidence в рамках существующего `Resolution`; пока применимый утверждённый исход не установлен, никакая финансовая операция или изменение refusal streak не производится. **Специально для дела после `client_accepted`:** до выполнения проверенных условий исключительного завершения §9.3.1 допустим лишь открытый `admin_resolution_pending` без денежного или терминального эффекта; истечение произвольного времени, сообщение участника или подтверждение наличия спора не превращаются в разрешённый исход. Такой case может оставаться ожидающим дальнейших доказательств и административного рассмотрения, не блокируя хранение истории и audit; автоматически закрывать его как успешно разрешённый запрещено.
3. Для noncash **одно применимое terminal financial outcome на один заказ**: общая сумма распределённых денег не превышает и не теряет фактически учтённые средства; по утверждённым формулам сохраняется точное равенство возврата клиенту, компенсации мастеру и доли Helpy с суммой соответствующего расчётного фонда. Ставки берутся из snapshot заказа; последующее изменение настроек Admin не пересчитывает этот исход. Для Cash не создаются platform refund/fee из отмены или False Call.
4. Зафиксированное решение и порождённые им финансовые обязательства должны быть связаны постоянными идентификаторами. Повторная команда Admin, повторный callback платёжного провайдера и повторное выполнение обработчика не создают второе решение, двойной возврат, компенсацию или комиссию. Состояния `requested/pending/confirmed/failed` внешних перечислений не подменяют собой бизнес-факт решения; неуспешная доставка денег не означает, что их разрешено отправить повторно как новую операцию.
5. Решение Admin не меняет задним числом исходный FAP, текст опубликованного задания, согласованную цену, время приёмки либо первичные доказательства. Попытка закрыть дело одновременно разными исходами и конкурентная команда обычного завершения проверяются относительно текущего состояния и атомарно допускают только один совместимый результат. Повторный просмотр дела остаётся возможен без повторного финансового исполнения.
6. Если решение требует возврата или выплаты, Domain Core формирует конкретные финансовые обязательства и неизменяемые события для последующего исполнения платёжным адаптером; для нулевых расчётных долей внешняя отправка не создаётся (§7.1, п. 8). Фактический способ возврата, поддерживаемые provider callbacks и техническая доставка денег относятся к внешнему платёжному слою; Domain Core не объявляет перечисление успешным до достоверного подтверждения.
7. Истечение `cancellationResponseTimeout` переводит безответный запрос в `admin_resolution_pending`, но **не выбирает финансовый исход за Admin**. Для исключительного обращения после `client_accepted` до порога/доказательств §9.3.1 запрещены `completed`, обычная отмена и любые новые `refund/payout/debt/commission`; допустим лишь открытый case без изменения заказа и held-средств. Равным образом достижение inactivity threshold само по себе не создаёт `completed`, payout или refund. Исключительное завершение уже принятой работы допускается только по отдельному подтверждённому решению Admin согласно §9.3.1.
8. Типизированные запреты и тесты: отсутствие необходимых подтверждений/оснований, конфликтующий терминальный исход, попытка применить False Call и обычную комиссию одновременно, превышение удержанных средств, второй финансовый эффект, использование устаревшего snapshot, неверная роль, решение о непринимаемой клиентом работе по правилу `client_accepted`, исполнение платежа с неизвестным исходом.

### 9.3. Noncash, payout, долг и inactivity

1. Payment states различают `initiated`, `pending`, `received`, `held`, `releasable`, `paid_out`, `failed`, `reversed/returned`; порядок/финансы и payout — **разные машины состояний**. Средства удерживаются до нормального completed либо согласованного resolution.
2. После подтверждённого `completed` единственный нормативный расчёт комиссии, округления, погашения долга и остатка мастера задают §7.2–§7.3. В §9.3 отдельная формула не определяется. Автоматическое перечисление положительного остатка производится по подтверждённому привязанному безналичному destination при доступном маршруте; без такого destination фактическое перечисление не инициируется, рассчитанное обязательство сохраняется. При нулевом остатке применить §7.1, п. 8: нет внешней операции, зафиксированный расчёт и `completed` сохраняются. Cash из методов выплат Helpy исключён. Ошибка payout не откатывает `completed`; при достоверном `failed` повторяется только исходящий перевод неизменного остатка по §7.3, при `pending/unknown` новая отправка запрещена до достоверного выяснения исхода.
3. Долг по комиссии возникает только после нормального `completed` Cash-заказа. **Глобальное начальное значение порога — 1000 THB только как Admin-configurable default**, не жёсткое ограничение. Для каждого мастера Admin может установить собственный порог, например 1000/2000/3000 THB или другое допустимое значение. Приоритет имеет индивидуальный порог; его изменение применяется к последующим проверкам доступности Cash, не переписывая зафиксированные финансы завершённых заказов. При достижении порога блокируется **только Cash**, а клиент видит **«Только безналичный расчёт»** до выбора мастера.
4. Рабочий чат без TTL: по прежней утверждённой политике первое напоминание через **36 часов** неактивности, последующие через **6 часов**, переход к exceptional-resolution **после 120 часов**. Все интервалы изменяемы через Admin; 120 часов не означают автоматическую отмену, возврат или выплату.
5. **Сроки хранения:** communication/evidence — начально **90 дней после terminal completion**, financial/audit/account — начально **1 год** по отдельной политике; сроки задаются через версионированную Admin policy с учётом применимых обязательных правовых ограничений (§11.5). Для financial/audit/account не подменять утверждённый срок автоматически 90-дневной точкой отсчёта коммуникаций: использовать явно закреплённую опорную дату конкретной записи и её применимую политику, не придумывая новое единое событие окончания хранения для всех типов. Сокрытие записи из пользовательской истории не удаляет canonical order/financial/audit. **Граница 90 дней:** её точка отсчёта определена здесь только для документированного `terminal completion` (`completed`). Для терминальной отмены, истечения без назначения и другого исхода без `completed` эта политика не даёт подтверждённого начального события: `eligibleForRetentionAction=false` для communication/evidence до появления отдельно утверждённой применимой нормы и достоверной опорной даты. Недостаток основания запрещает удаление, но не означает бессрочного обещанного срока хранения или автоматического распространения 90 дней на другие исходы; обязательные правовые ограничения соблюдаются независимо.

### 9.3.1. Контроль целостности завершения (технические инварианты существующих решений)

1. Отправка evidence мастером сама по себе **не является** приёмкой или завершением. Принятие результата клиентом и окончательное закрытие мастером — два самостоятельных авторизованных события; повтор любого из них не дублирует финансовые операции и не переводит заказ во второе `completed`.
2. После `client_accepted` средства noncash остаются удержанными, а комиссия по Cash ещё не превращается в задолженность мастера, пока не зафиксирован единственный переход в `completed` через `master_confirms_completion` либо через утверждённое исключительное завершение Admin по п. 7.
3. Один и тот же заказ не может одновременно перейти в normal `completed` и получить независимый terminal cancellation/resolution. Конкурирующие команды сверяют актуальное состояние; действующий `CancellationRequest` блокирует обычное завершение до его разрешения согласно §9.2.
4. Финансовые исходы cancellation/resolution нельзя дополнительно облагать стандартной комиссией, если уже действует отдельная согласованная формула. Повторное решение Admin, событие выплаты или перевод состояния не создают второй refund/fee/payout.
5. **Утверждено владельцем:** механизм длительного бездействия §9.3 распространяется и на `client_accepted`, когда клиент уже принял работу, но мастер не подтвердил окончательное закрытие. При отсутствии активности — первое напоминание через 36 часов, затем через каждые 6 часов; после 120 часов заказ становится доступен для `exceptional resolution` через Admin. Ни переход в `completed`, ни выплата, ни начисление комиссии/долга не выполняются автоматически по истечении срока. Интервалы настраиваются через Admin.

6. **Утверждено владельцем:** после `client_accepted` обычная отмена не допускается; особый случай разрешается через предусмотренный `Resolution`, а не через новый cancellation flow. При False Call распределение определяется `snapshottedFalseCallMasterShareRate`, а не неизменной пропорцией 50/50: доля Helpy округляется `half-up`, доля мастера — остаток от целой fee; сумма полностью сохраняется (§9.2 и §7.2).
7. **Утверждено владельцем — завершение Admin при бездействии мастера после приёмки:** если заказ находится в `client_accepted`, клиентская приёмка доказуемо зафиксирована, мастер не подтвердил закрытие и истёк применимый Admin-configurable порог бездействия (launch default — 120 часов), Admin вправе через существующий `exceptional Resolution` подтвердить окончательное завершение **вместо отсутствующего мастера**. До решения Admin проверяет историю заказа, подтверждение клиента и доступные evidence; результат содержит actor=Admin, основание, ссылку на приёмку и неизменяемое audit-событие. Принятая клиентом работа и FAP не изменяются. После подтверждённого решения заказ переходит в `completed` и запускает тот же **однократный** финансовый процесс, что и обычное завершение мастером: noncash становятся releasable, для Cash начисляется комиссия/долг по snapshot. Само истечение 120 часов **не** запускает `completed`, refund, payout или долг. Admin не получает полномочия завершать непринятую работу по этому основанию. При конкурентном подтверждении мастера/решении Admin только один переход в `completed` может быть успешным; повторная команда идемпотентна и не создаёт второго финансового эффекта. **В этом же единственном переходе `completed` сбрасывается `refusalStreak` мастера по §4.2**, как при нормальном завершении; история отказов не удаляется. Простое истечение срока без решения Admin, равно как повторная команда, счётчик не сбрасывает повторно.

### 9.3.2. Отзывы, репутация и история заказов — утверждённая семантика

**Нормативная граница:** правила отзывов, публичной репутации, истории заказов и модерации полностью определены настоящим §9.3.2 и проверками §13. Дополнительное чтение исторических блоков Registry об отзывах не требуется. Старые правила языкового ранжирования и квалификационного допуска не переносятся.

1. **Когда и кем:** после `completed` клиенту предлагается отдельная форма отзыва о назначенном мастере. Отзыв создаёт только клиент данного заказа; не более одного отзыва на завершённый `job_id`. Закрытие формы без отзыва допустимо и не блокирует новые заказы. Не создавать отзыв автоматически.
2. **Форма:** обязательная при отправке оценка от **1 до 5 звёзд**; необязательные множественные отметки **«Соблюдал договорённости»**, **«Работа выполнена аккуратно»**, **«Убрал за собой после завершения работ»**, **«Готов(а) обратиться к этому мастеру снова»**; необязательный текстовый комментарий. Отметки не являются требуемыми условиями завершения заказа.
3. **Показатели мастера:** публичные агрегаты рассчитываются **только по опубликованным и не скрытым Admin отзывам**: `workQuality` = средняя оценка по таким отзывам; `reliability` = число таких отзывов с отметкой «Соблюдал договорённости» / число таких отзывов; `reviewsCount` = число таких отзывов. `experience` = количество завершённых заказов **независимо от наличия или скрытия отзывов**. Отсутствие публично видимых отзывов не создаёт фиктивной оценки качества или надёжности; рейтинг показывается при наличии хотя бы одного видимого отзыва. Исходные отзывы сохраняются отдельно от публичной статистики.
4. **Доступность:** клиенту видны показатели и число отзывов; нажатие на число отзывов открывает доступный список комментариев. Показатели не дают преимущества в порядке ленты заказов мастера и не используются для профессиональной сертификации/допуска; Helpy остаётся посреднической площадкой. Новым мастерам не назначаются штрафные коэффициенты, фиктивные оценки или ограничения. Скрытые веса и временные коэффициенты запрещены.
5. **История:** оба профиля имеют пользовательскую историю завершённых заказов; начальный лимит отображаемого списка — **60**, изменяемый через Admin. Пользователь может скрыть завершённый заказ из **своего** списка, но это не стирает канонический заказ, отзыв, финансовые события, переписку, evidence и audit до окончания утверждённого срока хранения. Скрытие из истории не изменяет счётчик опыта и статистику отзывов.
6. **Утверждённая модерация отзывов:** отзыв клиента публикуется без предварительного одобрения Admin. При выявленном нарушении правил площадки уполномоченный Admin вправе **скрыть отзыв от публичного отображения**, сохранив исходную оценку, все отметки, оригинальный текст, `review_id`, `job_id`, автора, основание и неизменяемое событие модерации в истории. **Утверждено владельцем:** скрытый отзыв исключается из публичных `workQuality`, `reliability`, `reviewsCount` и публичного списка отзывов, но не меняет `experience` (число завершённых заказов) и не удаляется из канонического учёта. Admin **не вправе редактировать** текст клиента, оценку или отметки, подменять отзыв либо удалять оригинал по действию «Скрыть». Скрытие — изменение видимости, а не редактирование источника. Специального предварительного approval/review queue нет. Конкретный перечень нарушений и процедура апелляции этим решением не утверждались; SOL не должен придумывать их самостоятельно.
7. **Граница F2:** Domain Core определяет типизированный отзыв, право создания, однократность на завершённый `job_id`, показатели репутации, модерационную видимость, запрет редактирования содержания Admin и аудит основания скрытия; экран отзыва, Admin-UI и фактическая persistence-интеграция реализуются на последующих этапах. Изменение видимости не должно разрушать запись отзыва и историю. Влияние скрытого отзыва на публичные агрегаты определяется пунктами 3 и 6 настоящего раздела; вычисление и отображение должны использовать единый признак публичной видимости, не изменяя исходный отзыв.

| `client_accepted` | Admin проверил приёмку/историю и подтвердил `exceptional Resolution` после порога бездействия | `completed` | audit с основанием; финансовый эффект однократен, FAP неизменен |
| `completed` | повторная команда завершения или запоздавшая отмена | без изменения состояния и денежных обязательств | завершённый заказ не открывается вновь; повтор не создаёт комиссию, долг или payout |

| `cancellation_response_pending` | отсутствие ответа 8 ч | `admin_resolution_pending` | не считать молчание согласием |
| `cancellation_response_pending` | спор о partial work | `admin_resolution_pending` | нет автоматического списания по 15/30% |
| `assigned/working` | мастер запросил отмену с причиной вне утверждённых классификаций | `admin_resolution_pending` | без автоматической комиссии, штрафа, отказа, возврата или выплаты; noncash остаются held до обоснованного решения |
| `assigned/working` либо применимое незавершённое дело об отмене до `client_accepted` | доказанный добровольный отказ мастера, подтверждённый `ResolutionDecision` по §4.2 и §9.2 | structured cancelled | held noncash полностью возвращаются клиенту; отказ учитывается ровно один раз; после client_accepted этот исход не разрешён данным основанием |
| `completed` | payout failure | payout pending resolution | completed не откатывать |
| `assigned/working` | inactivity: применимый порог (launch default 120 ч) | exceptional-resolution eligible: административное рассмотрение по §9.2–§9.3 | нет автоматического завершения/отмены/refund/payout; исключительное завершение по §9.3.1, п. 7 недоступно без подтверждённой приёмки клиента |

## 11. Краевые случаи — проверенные пределы действующих решений

### 11.1. Досрочное завершение переговоров

**Граница операций:** закрытие окна чата и подтверждённое «Завершить переговоры» имеют разные последствия, определённые в §4.2 и нормативной матрице §5.1; применимый тайм-аут не создаёт отдельного таймера для Final Application. Административное закрытие временного чата регулируется §5.1; ручное продление жизненного цикла чата отсутствует.

**Досрочные исходы:** все правила первого и повторных циклов, двусторонней защиты, досрочного завершения чатов, вариантов A/B и сохранения `job_id`/снимка определяются §5.1. Настоящий раздел не вводит дополнительных переходов.

### 11.2. Неопределённый результат провайдера

Если клиент успел инициировать payment operation до окончания payment-selection окна, то отсутствие окончательного ответа провайдера **не переводит** операцию в failed и не освобождает мастера автоматически. Используется отдельный provider confirmation timeout/status. Только доказанный первый terminal `failed` однократно сбрасывает тот же Admin-configurable счётчик оплаты (launch default 600 секунд); terminal `success` немедленно завершает assignment; дубликаты и запоздалые callbacks не создают двойных назначений или списаний. Если статус в provider window неизвестен — вернуть typed `PaymentOutcomeUnknown`, сохранить reservation и передать состояние в предусмотренную provider/operational resolution, а не изобретать автоматический финансовый исход. **Это же правило имеет приоритет над автоматическим освобождением резерва при истечении счётчика (§6.1); до достоверного исхода запрещены Cash и второй платёж.** Значение provider confirmation timeout задаётся адаптером/операционной policy, не приравнивается к 600 секундам клиента.

### 11.3. Уведомления, пользовательские настройки и сообщения Helpy — утверждённые границы

**Действующая область:** уведомления Client/Master/Admin, настройки пользовательских оповещений, Platform Inbox, Feedback и официальный Support Chat определяются правилами настоящего §11.3 и §11.3.1. Эта область **не** является механизмом проверки квалификации, ранжирования или допуска мастеров к заказам. Для реализации не требуется открывать прежние продуктовые контракты либо отдельную историческую архитектуру Notification Center.

1. **Назначение:** Domain формирует типизированное `NotificationEvent` по подтверждённому бизнес-событию и его фактическим адресатам. Отправка уведомления не изменяет `Job`, `Offer`, `Chat`, `Payment` и не подменяет бизнес-событие. Повторная доставка или обработка того же события не создаёт повторного перехода и не должна превращаться в бесконечную рассылку дублей.
2. **Обязательные события:** мастер получает уведомление о **новом опубликованном заказе, подходящем и фактически доступном по выбранной им специализации**; клиент — о **новом предложении мастера** по заказу. При закрытии срока публикации с завершением заказа клиент получает уведомление; при выборе мастера участники остальных временных чатов получают сообщение об их закрытии. Иные уведомления, явно предусмотренные настоящим контрактом, сохраняются: ошибки/статусы платежа, приёмка/завершение, отмены и Resolution.
3. **Исключённые участники:** отклонённый клиентом мастер, мастер с отказом и мастер с естественно завершившимся временным чатом **не получают** новых уведомлений о повторной публикации **того же `job_id`**. Специализация определяет релевантность заказа; язык, география, рейтинг и квалификационные проверки не добавляются как фильтры уведомлений.
4. **Напоминания:** временные переговоры — через час и затем каждый час **только стороне, от которой ожидают ответа** (§5); Cancellation Request — по исходным 8 часам / 30 минутам (§9.2); рабочая стадия и `client_accepted` — 36/6/120 часов (§9.3). Все времена фиксируются при запуске соответствующего отсчёта по §11.5, п. 5; напоминание **не является** согласием, отказом, закрытием заказа или оплатой. Языковое указание мастеру в чате до его ответа (§5) — отдельное сохраняемое состояние диалога, а не одноразовое исчезающее push-уведомление.
5. **Предпочтения:** Client и Master имеют собственные пользовательские настройки уведомлений. Helpy фиксирует основание, получателя, тип события, состояние и попытку отправки через подключаемый канал; фактический способ доставки и звук зависят от настроек приложения, разрешений ОС и режима устройства. Helpy не гарантирует звук при запрете ОС или отключении пользователем. Управление глобальными интервалами и параметрами уведомлений предусмотрено через Admin. Конкретные каналы доставки и UI-контролы реализуются позднее; в F2 задаются конфигурация, типизированные события и независимые порты, не привязанные к Firebase, ОС или конкретному push-провайдеру.
6. **Доступ и конфиденциальность:** событие адресуется только стороне, имеющей отношение к конкретному заказу/предложению/чату. Уведомления не раскрывают полный адрес клиента до окончательного назначения мастера, содержимое чужих переговоров или закрытые служебные контакты.
7. **Официальная связь с платформой:** сохраняются **Platform Inbox + Feedback** для односторонних системных сообщений и форм обратной связи. **Дополнительно по решению владельца от 16.11.2026** платформа вправе открывать отдельный **двусторонний Support Chat Helpy ↔ Master / Client** при обстоятельствах, требующих участия Admin (§11.3.1). Это не отдельный заказной чат: он использует общий механизм долговременной переписки, но изолирован по участникам, назначению и правам. В частности, сообщения поддержки не заменяют структурированные Cancellation / Resolution / Payment / DebtRepaymentRequest и не являются самостоятельным основанием для финансового изменения.
8. **Граница F2:** определить `NotificationEvent`, `NotificationPreference`, назначение адресата, события напоминаний, состояние доставки и интерфейсы к адаптерам; отдельно — типизированные Platform Inbox/Feedback и Support Chat contracts, role access и связь с предметными обращениями. Реальная доставка, экраны переписки, форма обратной связи, раздел поддержки и Admin Notification Center выполняются на соответствующих последующих этапах. Не включать неутверждённые рекламные рассылки, произвольные каналы или новые таймеры.

### 11.3.1. Официальный двусторонний чат поддержки Helpy — решение владельца от 16.11.2026

1. **Назначение и стороны.** Когда вопрос требует участия администрации, уполномоченный Admin может инициировать личный диалог службы поддержки **Helpy ↔ конкретный Client** либо **Helpy ↔ конкретный Master**. Пример для Master — заявка на добровольное погашение долга (§7.0.1), включая согласование наличной передачи или безналичного перевода. Для Client — обстоятельства, требующие административного решения, в том числе связанные с уже предусмотренным `Admin Resolution`. Чат предназначен для понятной официальной связи внутри приложения, чтобы адресат видел, что обращается именно служба Helpy, а не неизвестный внешний контакт.
2. **Подлинность отправителя.** На пользовательской стороне отправитель отображается как **«Служба поддержки Helpy»**, а не как личный аккаунт мастера, клиента или неустановленный номер. Право создания официальной беседы и отправки сообщений от имени Helpy проверяется серверным доменным разрешением по подтверждённой роли Admin; простой визуальный значок, имя и локальная настройка UI не подтверждают подлинность. Сообщения содержат внутреннюю идентичность авторизованного сотрудника в закрытом audit, тогда как пользователю показывается единая служба поддержки. Обычный Client/Master не вправе подделать системного отправителя или просматривать чужой Support Chat.
3. **Единое ядро переписки.** Используются существующие принципы долгоживущего `ChatThread`/`ChatMessage`: упорядоченная история, непрерывность диалога после повторного входа, двусторонние ответы, оригинал сообщения без перезаписи и отдельное переводное представление TH/RU/EN. Это **общая чат-инфраструктура и правила сообщений**, а не копия нового chat core. У Support Chat — **самостоятельный `chat_id` и тип** `support`, с участниками «Helpy + один пользователь»; он **не присоединяется** к переговорному/рабочему `chat_id` пары Client–Master, не раскрывает их личную переписку и не меняет участников рабочего заказа.
4. **Долгосрочный жизненный цикл.** Официальный диалог остаётся доступным и сохраняет историю при смене экранов, повторном входе и завершении связанного заказа; завершение `Job` или отдельной `DebtRepaymentRequest` не удаляет переписку и не переводит её автоматически в режим запрета сообщений по §5. Открытие, ответ, завершение отдельного обращения и доступ к истории должны быть явными типизированными состояниями/действиями поддержки; для Support Chat не применяются TTL публикации 24/12/6/3, правило защиты переговоров, ограничение первой фотографии по стадии заказа или автоматические правила выбора мастера. Общее файловое вложение не разрешается только потому, что рабочий чат допускает фото: его разрешения определяются отдельно, без выдуманного лимита и без обязательной реализации нового канала на F2.
5. **Привязка к основанию без подмены решений.** Для предметного обращения Support Chat хранит ссылку на разрешённую сущность/основание (`DebtRepaymentRequest`, `AdminResolutionCase` или иной уже предусмотренный административный случай). Диалог — место для согласования и объяснений, а не самостоятельный финансовый реестр. Никакое текстовое «оплачено», «согласен», статус прочтения или закрытие беседы не уменьшает долг, не подтверждает Cash/Noncash, не назначает мастера, не отменяет заказ и не утверждает Admin Resolution: только отдельный авторизованный UseCase с доказательствами и audit меняет соответствующее состояние.
6. **Доступ, события и уведомления.** Создание беседы/новое сообщение формирует адресованное уведомление нужному Client/Master или Admin; пользователь отвечает **только в своём** Support Chat. Применяются те же базовые гарантии идемпотентной доставки, конфиденциальности, ролевого контроля, сохранения сообщений и согласованной истории, что и для основного чат-механизма. Ни пользователь, ни Admin не получают доступа к посторонним заказам, финансовым фактам и разговорам только по факту участия в чате. Общедоступный Platform Inbox и Feedback сохраняют собственные назначения и не заменяются Support Chat.
7. **Нормативная граница F2/F3+.** На F2 обязательны типизированные модели/варианты `ChatThread` (заказной и официальный support), идентичность участников, разрешения и состояния, ссылки на основание, UseCases начала беседы и обмена сообщениями, repository/notification ports, типизированные ошибки и тесты. Mobile/Admin UI, визуальное оформление «Служба поддержки Helpy», реальная доставка, медиаадаптеры и эксплуатация операторского рабочего места относятся к соответствующим последующим этапам. Нового независимого backend или переводчика только для поддержки не создавать.

### 11.4. Учётная запись, независимая активация ролей и контакты — действующие требования F2

**Нормативность:** модель идентичности, входа, независимых ролей и локализации полностью определяется настоящим §11.4 и общими правилами §1. Legacy-ограничения одной роли, обязательного телефонного входа и предварительного профессионального одобрения мастера не применяются. Дополнительное чтение прежних контрактов для реализации не требуется.

1. **Методы входа на запуске:** Google, Email OTP, Phone OTP. Доменные модели не зависят от конкретного поставщика аутентификации и допускают добавление методов позднее. Доверенно подтверждённый email от Google удовлетворяет требованию `verified email` без повторного Email OTP; если провайдер не подтвердил email, подтверждение необходимо отдельно до активации нужной роли.
2. **Идентичность:** у пользователя один стабильный внутренний `user_id`, не зависящий от способа входа, имени и языка. Успешный вход создаёт учётную запись, но **не означает автоматическую активацию профиля роли**. После первой аутентификации доступен onboarding соответствующей роли.
3. **Две роли на одном аккаунте:** один `user_id` может иметь независимо активированные `ClientProfile` и `MasterProfile`. Активация одной роли не активирует другую; при наличии обеих пользователь переключает активную роль без создания второй учётной записи. Доступные действия определяются активной ролью; при этом данные заказа защищены фактическим участием в конкретном заказе, а не одним лишь названием роли.
4. **Условия активации Client:** подтверждённый email и Display Name. Телефон необязателен, фотография профиля необязательна.
5. **Условия активации Master:** подтверждённый email, подтверждённый телефон, Display Name, фотография профиля и выбранные самим мастером категории/сущности специализации. **Это полнота профиля, а не сертификация профессии:** Helpy не проверяет квалификацию мастера и не вводит дополнительные разрешения на оказание услуг. Специализация используется только для фильтрации подходящих заказов по уже принятому правилу §4.
6. **Разные входы без привязки:** вход через другую непривязанную identity создаёт отдельную учётную запись; автоматического слияния аккаунтов нет, ручное слияние на запуске не требуется. Пользователь может привязать подтверждённые телефон или email к своему аккаунту. Если такая identity принадлежит другому аккаунту, привязка не выполняется и пользователь получает понятное сообщение; существующий аккаунт автоматически не объединяется.
7. **Контакты и приватность:** служебные контактные данные (телефон, email, LINE, WhatsApp и будущие каналы) доступны владельцу аккаунта и уполномоченному Admin, но не раскрываются другой пользовательской роли. Между Client и Master используются Display Name, разрешённая фотография профиля и внутренний чат Helpy. Правила выдачи адреса по §4 сохраняются.
8. **Восстановление доступа:** через email владельца существующей учётной записи; доменная операция восстановления разрешается только после достоверного подтверждения контроля привязанного к этому `user_id` email через заменяемый identity-provider port. Запрос сам по себе, неподтверждённый/чужой email и повторное предъявление уже использованного подтверждения не дают доступа к аккаунту, не создают новую identity и не меняют привязки или роли; детали реальных OTP/токенов остаются за F3+. Выбранный язык интерфейса не зависит от метода входа; переключение `th/ru/en` не создаёт новую identity и не меняет активацию ролей.
9. **Учёт в Admin:** один пользователь с обеими активными ролями учитывается как один активный `ClientProfile` и один активный `MasterProfile` (две учётные роли, не две учётные записи). Online/presence — отдельное оперативное состояние, а не постоянное поле профиля.
10. **Граница F2:** типизированные `User`, `AuthIdentity`, `ClientProfile`, `MasterProfile`, `RoleActivation`, `ContactBinding`, проверки полноты и uniqueness, role-aware access и порты аутентификации/профиля. Реальный Google/OTP провайдер, токены, хранение секретов, экраны onboarding и Admin UI реализуются на последующих этапах, не как зависимость Domain Core.

**Обязательные тесты F2:** создание `User` без активного профиля; независимая активация Client/Master и переключение ролей; корректная проверка подтверждённого email Google и отдельного email для Phone OTP; обязательный телефон только для Master; разрешение отсутствующей фотографии Client и запрет активации Master без фото/специализации; отказ привязки уже занятой identity без merge; защита служебных контактов; сохранение идентичности при смене локали; корректный подсчёт обеих ролей в Admin. Отдельный защитный тест восстановления доступа: подтверждение email через фейковый identity-provider port возвращает доступ именно прежнему `user_id` с прежними ролями; неподтверждённый адрес, email другой учётной записи, просроченное/повторно использованное подтверждение и конкурирующий повтор не дают чужого доступа и не создают дубликат; отсутствие реального OTP/email-адаптера не является FAIL F2. Все проверки через фейковые порты и без реальных OTP-сервисов.

Положительный тест использует утверждённое начальное значение либо явно заданную допустимую редакцию; отрицательный — значение, нарушающее соответствующий тип или инвариант.

Для структурных настроек, где продуктовый максимум или возможность отключения отдельного функционала **не утверждены**, F2 проверяет перечисленные общие инварианты, а не придумывает дополнительные численные пределы и бизнес-запреты. Каждая строка реестра §11.5 должна иметь хотя бы один конкретный положительный и отрицательный сценарий с типизированным результатом по §12.2–12.3; синтетическое `invalid` без нарушения названного инварианта не считается тестом.

**Правила настройки:**
1. Для утверждённых финансово значимых ставок действует версионирование, время вступления в силу и audit. `FinancialSnapshot` создаётся при подтверждённом выборе мастера; последующее изменение комиссии, ставок отмены и False Call не пересчитывает зафиксированные обязательства. Исторический источник версии остаётся доступен Admin Resolution.
2. Порог задолженности поддерживает явные **индивидуальные** настройки мастера и глобальное значение по умолчанию. Порог проверяется при показе доступности Cash и повторно при выборе метода; настройка может изменить **будущую** возможность Cash без пересчёта комиссии старого заказа. Нельзя превращать превышение порога в блокировку безналичных заказов или фильтр профессиональной пригодности. **Формула автоматического удержания (§7.3) не является Admin policy: ставка фиксирована 70%, global/per-master override отсутствует.** Добровольное погашение по §7.0.1 оформляется в целых THB, только наличными либо безналичным переводом на счёт Helpy; Admin подтверждает фактически полученную сумму, а не устанавливает процент удержания.
3. Поддерживаемые платежные и payout методы — **два независимых конфигурируемых набора**; отключённый способ нельзя предлагать для новой операции. В рамках F2 не реализовывать сами платёжные интеграции или Admin-формы, но предоставить типизированные конфигурационные интерфейсы и доменные проверки.
4. Правила управления каталогом и информационными блоками определены §2.3 и §3.2–§3.3. Опубликованные редакции, зафиксированные условия и исторические ссылки сохраняются; корректировка перевода допустима только по §3.3.
5. **Утверждено владельцем — условия на момент создания (вариант A):** каждый таймер публикации, повторного цикла, напоминания, оплаты, cancellation или inactivity при запуске фиксирует действующую версию Admin-настройки, продолжительность и рассчитанный `deadline`. Последующее изменение настройки **не пересчитывает и не продлевает уже действующий отсчёт**. Для первого цикла это также означает неизменность зафиксированного наличия/отсутствия автоматического deadline (§5.1). Ручное административное продление чата не предусмотрено. Новое значение применяется только к новому запуску соответствующего таймера/цикла; при следующем цикле повторной публикации или однократном разрешённом сбросе счётчика оплаты берётся версия настройки, действующая на момент запуска нового отсчёта. Финансовые условия уже выбранного заказа остаются по `FinancialSnapshot` без пересчёта. Сохранённый `deadline` и версия policy восстанавливаются после перезапуска и проверяются серверной доменной логикой; платёжный provider `pending/unknown` продолжает защищать резерв независимо от истечения таймера.
6. Общая роль Admin — управление утверждёнными параметрами и рассмотрение предусмотренных дел, а не контроль профессиональной квалификации мастеров. Управление репутацией ограничено утверждённой модерацией отзывов. Нет разрешения Admin изменять опубликованное ТЗ, подтверждённую FAP или первичное сообщение.

**Граница этапов:** F2 реализует `PolicyDefinition`, типизированные значения и их проверку, разрешение глобального/персонального значения, версии/effective-time, ссылки на snapshots, доменные переходы и фейковые порты для тестов. F3 предоставляет хранение и адаптеры. Экранные конструкторы каталога, панели редактирования параметров, фактические каналы оповещения и подключения платёжных провайдеров выполняются на последующих утверждённых этапах. Наличие будущего Admin UI в требованиях **не означает** его реализацию внутри F2.

**Тесты автоматического и добровольного погашения (§7.3 и §7.0.1):** (а) при одинаковой комиссии и долге для разных мастеров применяется одна формула с 70%, независимо от индивидуального Cash-порога; (б) попытка Admin установить глобальную или индивидуальную ставку удержания, передать иной коэффициент в расчёт либо изменить созданный payout отвергается без изменения долга/расчёта; (в) повторный provider callback, payout retry и перезапуск не создают повторного удержания; (г) два конкурентных payout не списывают один и тот же долг дважды; (д) долг меньше лимита удержания — удерживается не больше долга; (е) voluntary repayment наличными либо переводом без подтверждения Admin не уменьшает остаток; после подтверждения уменьшает его однократно; (ж) изменение Cash-порога не влияет на формулу; третий способ добровольного погашения, в том числе отработка заказов или индивидуальная ставка, отвергается без финансового эффекта.

**Точный защитный тест №04 — неуспешный исходящий payout после завершённого безналичного заказа:**

- **Исходные факты:** `PaymentOperation=success` на полные `1000 THB` до назначения мастера; заказ штатно завершён `completed`; финансовый snapshot фиксирует комиссию `30%`; ранее существующий Cash-долг мастера `300 THB`; фиксированная нормативная ставка удержания `70%`.
- **Первичный результат расчёта:** комиссия Helpy `300 THB`, погашение долга `300 THB`, `outstandingDebt=0 THB`, единственная сумма обязательства к перечислению мастеру `400 THB`. Заказ остаётся `completed`, а клиентский платёж — `success`.
- **Сбой перечисления:** исходящая операция перечисления `400 THB` получает достоверное `failed`, причём средства не ушли мастеру и остаются у Helpy. Проверить: `outstandingDebt=0 THB`, обязательство перед мастером по-прежнему `400 THB`, повторная комиссия и повторное удержание **не возникают**.
- **Повтор:** повторная попытка перечисляет **только те же `400 THB`** по идентичному неизменному расчёту, используя безопасный уникальный ключ операции; результат `success` погашает обязательство перед мастером ровно один раз. Повтор события `success`, перезапуск обработчика и изменение разрешённых Admin-настроек не меняют ни долг, ни сумму payout.
- **Неопределённый исход:** если вместо достоверного `failed` провайдер возвращает `pending/unknown`, новая исходящая отправка **не инициируется** до подтверждённого разрешения предыдущей попытки. Проверить отсутствие двойного перечисления и неизменность `outstandingDebt`.
- **Ограничение области:** тест выполняется с фейковыми `Ledger`, `MasterPayout` и provider-port; не требует реального банка, Worker, D1 или изменения этапа F1. Это защита утверждённого жизненного цикла, а не новый финансовый сценарий.

**Исчерпывающая проверка реестра Admin policy (§11.5):** параметризованная таблица тестов обязана включать **каждую строку реестра**, а не выбранную подвыборку. Для каждой настройки зафиксировать её собственный тип, утверждённое начальное значение либо отсутствие утверждённого числового default, допустимые/недопустимые значения, применимый UseCase, права изменения Admin, разрешение актуальной версии, проверку воздействия на **новое** событие и неизменность уже зафиксированного факта. Для параметров, где предусмотрен индивидуальный override, проверить `per-master → global → initial policy`, явное снятие override и независимость мастеров. Для каталогов/форм/локалей — версии Published и неизменность снимков; для публикации, напоминаний, оплаты, отмены и inactivity — исходный/новый deadline через fake Clock; для методов client payment и master payout — два независимых набора; для комиссии, Cash threshold, mutual/False Call — актуальную политику, момент snapshot, half-up и изоляцию historical obligations; для истории и уведомлений — действующие лимиты/настройки без изменения canonical facts и фильтра ленты. Параметр provider confirmation timeout не получает выдуманного числа: тест принимает явно заданную валидную policy либо возвращает типизированную невозможность запуска при отсутствии обязательной конфигурации. **PASS** строки допускается только при наличии позитивного и негативного теста конкретного UseCase, наблюдаемого результата и реального исполнения; отсутствие одной строки/неверная точка фиксации или ретроактивная мутация — **FAIL**. Отдельная физическая реализация Admin UI не требуется на F2.

**Тесты retention policy (§9.3 п.5; §11.5):** с управляемым `Clock` проверить независимые начальные сроки `communication/evidence = 90 дней после terminal completion` и `financial/audit/account = 1 год`, а также разные Admin-версии, опорные времена предметных записей и действующие правовые ограничения. За мгновение до применимого дедлайна доменная оценка `eligibleForRetentionAction` запрещает удаление; по достижении дедлайна только определяет допустимость дальнейшей операции при отсутствии правового ограничения, не удаляя данные в F2. Проверить, что скрытие заказа из истории и скрытие отзыва не запускают удаление, а изменение retention policy не пересчитывает уже зафиксированные финансовые события. Отрицательные тесты: отсутствие terminal completion для 90-дневного отсчёта; отдельные случаи `cancelled`, `expired` и unresolved `Resolution` без `completed` → `eligibleForRetentionAction=false` даже после 90 дней от иной даты; подмена 1 года 90 днями, неверная опорная дата, правовое ограничение, неавторизованная настройка. Физические purge/SQL/storage-adapter — F3+; сами тесты проверяют только чистую доменную политику.

**Тесты финансовой согласованности (§7.2–§7.3; §9.2 п.6):** при `netBeforeDebt=105 THB`, фиксированной ставке `70%` и достаточном долге удержание равно `74 THB` (73,5 → 74), остаток мастеру `31 THB`; при `netBeforeDebt=101 THB` удержание равно `71 THB` (70,7 → 71), остаток `30 THB`. Результат immutable после создания payout. Отдельно: при netBeforeDebt=1 THB и долге не менее 1 THB удержание после half-up равно 1 THB, остаток 0 THB; при нулевом netBeforeDebt удержание и остаток равны нулю. Зафиксировать расчёт, не инициировать внешнюю отправку 0 THB. Для разрешённого Cancellation/Resolution проверить нулевую долю и положительные доли: отсутствует внешняя операция на ноль, фонд сохраняется, положительные доли не меняются. Проверить также отсутствие внешней отправки без подтверждённого destination для положительного штатного payout и сохранение рассчитанного обязательства (§9.3). Для partial-work `FAP=101 THB`, ставка комиссии `30%`, `heldAmount=101 THB`: `snapshottedCommission=30 THB`, `settlementPool=71 THB`; суммы возврата и компенсации должны быть целыми и в сумме давать `71 THB` при любом утверждённом решении Admin, без дробных THB и повторного округления комиссии. Обязателен негативный тест на расхождение фонда из-за независимого округления.

**Дополнительные тесты F2:** изменение глобального Cash-порога, individual override порога у двух мастеров, снятие override порога и возврат к global; snapshot FAP/commission/cancellation после изменения Admin; видимость и серверная проверка Cash; переключение доступности независимых client payment / master payout routes; сохранение Published-конфигурации и исторического заказа; истечение исходного и пустого повторного цикла; notification/cancellation/inactivity timers через фейковый `Clock`; отсутствие обязательной реализации UI/DB в Domain. Тесты политики времени обязательны: изменение Admin-длительности при действующем таймере не меняет его сохранённый `deadline`; переключение автозакрытия в обе стороны не меняет наличие/отсутствие deadline уже начатого первого цикла; новые первые публикации используют актуальный флаг; вновь созданный таймер/следующий цикл получает актуальную версию настройки; восстановление после перезапуска сохраняет остаток; истечение таймера во время provider `pending/unknown` не освобождает резерв.

### 12.2. Типизированные результаты, согласованность и границы адаптеров

1. **Не только DTO.** Каждая доменная операция возвращает типизированный успех с изменёнными предметными фактами и/или набором доменных событий либо конкретный typed Failure. Недопустимо подменять инварианты проверками Flutter, HTTP handler, SQL constraint или моковым успешным ответом.
2. **Проверка роли и факта:** UseCase выполняет разрешение действия по реальному состоянию агрегата, активной роли и соответствующему actor; скрытие кнопки в UI само по себе не является авторизацией. Для чужих заказов, чатов, отзывов, финансовых записей и Admin-действий необходимы отрицательные тесты.
3. **Один исход при конкуренции:** публикация согласованной языковой версии (§3.3), закрытие переговоров и выбор мастера, назначение после оплаты, завершение, отмена, Admin Resolution, начисление долга и выплаты должно быть согласованно по версии состояния и уникальному бизнес-основанию. Конкретный механизм блокировок/транзакций — задача Data/Backend F3; F2 задаёт контракт атомарного изменения и проверяет конкурирующие вызовы через подменяемый порт.
4. **Никаких вымышленных provider events:** `pending/unknown` не преобразуется в `failed` только из-за истечения UI-счётчика; провайдерские результаты и повторы связаны с идентификатором операции, а не только `job_id`. Domain возвращает типизированное `needsResolution` с `operation_id`, текущим достоверным состоянием, зафиксированным deadline и причиной запрета повтора; оно **не** является `failed` или разрешением повторной отправки. Для платежа резерв и запрет альтернативных методов сохраняются, для payout повтор не отправляется. Только отдельно подтверждённый достоверный исход конкретной операции снимает соответствующую блокировку по уже утверждённым условиям. В F2 это проверяется через фейковый provider port; выяснение исхода у банка, webhook/payment adapter и операционный регламент относятся к F3+, а неопределённый provider timeout не получает выдуманного значения.
5. **Clock и snapshot:** каждый срок привязан к сохранённой точке отсчёта и принятой версии Admin policy; доменная проверка времени использует инъецированный Clock. Все финансовые суммы — целые THB; функции распределения обязаны сохранять сумму и выполнять уже утверждённое округление.
6. **Границы реализации:** в F2 запрещены код реального Worker/D1, UI Mobile/Admin, SQL-миграции, сетевые SDK, реальные SMS/OTP, переводческие и платёжные интеграции, файловое хранение. Для них определяются только необходимые бизнес-порты и контракты. Реализация каталогов/конструкторов и фактическое наполнение форм на последующем этапе не освобождает F2 от тестирования универсального механизма на утверждённых эталонах 8/31.
7. **Доказательная трассировка:** для каждого самостоятельного применимого к F2 нормативного требования из §1–§11 и дополнительных обязательных требований к проверкам, процедуре и границам из §12–§15, включая все составляющие каждой строки §12.1 и все отдельные обязательные проверки §13, исполнитель предъявляет уникальный идентификатор нормы (§, пункт/строка и при необходимости локальный порядковый суффикс), имя и путь реального серверного UseCase/Domain, типизированный вход/успех/Failure, используемый порт (или обоснование его отсутствия), идентификаторы и пути **запущенных** позитивного и негативного тестов, фактическую команду, exit code и первичное свидетельство результата. Тесты проверяют реальные переходы и долговечные инварианты через фейковые порты, не просто создание DTO; хотя бы один сценарий повторной/конкурентной операции нужен для финансовых/платёжных случаев. Для настроек §11.5 требуется отдельная строка доказательств на каждый параметр; для retention и email recovery — отдельные доказательства из тестов выше. Отсутствие положительного либо отрицательного теста, запуска или свидетельства даёт **FAIL/NOT RUN**, а не декларативный PASS; отсутствующий реальный адаптер F3 не является дефектом F2. Для структурных, архитектурных, запретительных и процессных норм, не являющихся самостоятельной бизнес-операцией, вместо искусственного UseCase указать проверяемый объект, применимый архитектурный/статический/регрессионный тест либо контроль процедуры, критерий PASS/FAIL и фактическое свидетельство. Поля операции, порта и typed Failure, неприменимые к такой норме, обосновать; это не освобождает от проверки самой нормы.
8. **Проверка полноты:** до реализации составить полный индекс самостоятельных норм по п. 7 и сопоставить его с §12.1, §11.5 и обязательными проверками §8, §11 и §13. Повторные формулировки одной нормы могут ссылаться на единый идентификатор; каждое добавочное самостоятельное условие проверяется отдельно. Одна строка матрицы может охватывать несколько норм; каждую проверить отдельно по п. 7. Один тест допускается использовать для нескольких норм только при явном сопоставлении конкретных проверяемых утверждений. Для требований будущих этапов явно указать отложенный gate и проверяемую в F2 доменную границу, без ложного PASS UI/Infrastructure. Не создавать второй нормативный контракт. Норма без покрытия либо обоснованной границы этапа блокирует приёмку.

## 13. Состав реализации SOL 6.1 (после приёмки владельцем)

**В серверном TypeScript Domain/Application принятого `apps/backend`**, без отдельного Dart-серверного ядра и без реализации серверных правил в Mobile: Domain models, typed interfaces, UseCases, typed Failures и конфигурационные контракты для всех разделов §1–§11, включая отдельный жизненный цикл `Offer` и отправку `Final Application` по §4.1. Самостоятельно тестируемые state transitions для заказа, offer, chat, payment operation, held funds, cancellation, settlement, payout и master debt; семантика каталога и форм без привязки к имени услуги. Обязательные тесты §8 включают полный жизненный цикл `DebtRepaymentRequest`/`DebtRepaymentReceipt` по §7.0.1, включая официальный двусторонний Support Chat по §11.3.1 для согласования с мастером, с отдельным подтверждением Admin и идемпотентным учётом поступлений; расширяются проверкой идемпотентности двух подтверждений, конкурентного завершения/отмены, запрета штатного payout/начисления Cash-комиссии в долг до `completed` (не подменяя им разрешённые cancellation/Resolution compensation/refund по §9.2), тестами acceptance/rejection из `assigned` и `working` без обязательных `work_started` и evidence, запрета обычного завершения до assignment и при действующем CancellationRequest, двухступенчатого completion, cancellation 8 ч / reminder 30 мин, mutual 15%, False Call 30%/split, partial-work admin settlement, cash exclusion, payout retry, признанного добровольного отказа через Resolution из допустимого предшествующего клиентской приёмке контекста отмены с полным noncash refund и однократным учётом отказа, inactivity 36/6/120 ч, включая `client_accepted` без автоматического завершения, и разрешённого вручную Admin exceptional completion при подтверждённой клиентской приёмке (для `assigned/working` без клиентской приёмки порог inactivity даёт только возможность рассмотрения, не право завершить работу; audit, неизменность FAP, один финансовый эффект при конкурирующем закрытии мастером), запрета обычной отмены после `client_accepted` с отдельным exceptional Resolution, **параметризованного** False Call settlement: тесты начальных ставок 30%/50%, изменённой доли мастера (например, 40%), неделимой fee (31 THB), использования неизменных ставок snapshot после изменения Admin, равенства `clientRefund + masterCompensation + helpyShare = FAP` и отсутствия дополнительной комиссии, полной неизменяемости snapshots и role access. Проверка Admin Resolution дополнительно включает: повторные решения/события провайдера, согласованное распределение целых THB без потерь, запрет двойной комиссии и взаимоисключающие terminal outcomes, сохранение immutable evidence/snapshot, корректные роли и отсутствие автоматического исхода по таймерам. Обязательный тест: отмена по инициативе мастера без доказанного добровольного отказа, False Call или partial work переводит case в `admin_resolution_pending`, сохраняет held noncash и не создаёт штраф, начисление комиссии, изменение refusal streak, refund либо payout до подтверждённого Resolution. **Отдельный E-01-тест:** `client_accepted` + исключительное обращение до применимого порога 120 часов (или до иных обязательных доказательств) оставляет `ResolutionCase` в `admin_resolution_pending`, исходный заказ в `client_accepted`, noncash в `held`; запрещены обычная cancellation, `completed`, refund, payout, commission и изменение debt/refusal streak. Повторная/конкурентная команда Admin не создаёт terminal outcome; позднее допустимо только отдельно подтверждённое исключительное завершение при выполненных условиях §9.3.1. Никаких ложных PASS без запуска реальных доменных тестов.

**Тесты управления каталогом и языковыми редакциями:** обязательны §8, п. 1–2 и соответствующие строки §12.1; доказательства по §12.2–§12.3.

**Тесты регистрации и восстановления аккаунтов:** по §11.4 обязательны восстановление подтверждённой исходной identity через email, отказ в доступе по чужому/неподтверждённому адресу, повторному токену/claim и отсутствие появления второго `user_id`; реальные OTP/email-сервисы не требуются.

**Тесты E-04 provider uncertainty:** фейковый provider-port возвращает `unknown` после истечения клиентского deadline: доменный результат `needsResolution` содержит исходный `operation_id`, reserved master остаётся reserved, второй платёж/Cash запрещены и внешнее `failed` не выдумывается. Для `MasterPayout` с неизвестным исходом не создаётся новая отправка; после достоверного `failed` повторяется только неизменная сумма мастеру. Наличие реального банковского подтверждения или ручного UI в F2 не требуется.

**Тесты покрытия политик и сроков:** §11.5 — каждый реестровый параметр через таблицу кейсов default/override/version/snapshot/invalid, где применимо; §9.3 — 90-дневное окно после terminal completion для communication/evidence, независимый год для financial/audit/account, действие юридических ограничений, изоляция физического удаления на F3. §9.2 и §7.3 — числовые тесты half-up и сохранения целого фонда без второй формулы расчёта; обязательны проверки фиксированных 70%, запрета Admin override автоматического удержания и двух способов добровольного погашения по §11.5.

**Тесты отзывов/истории:** 1–5 звёзд, пустые необязательные отметки и комментарий, запрет отзыва до `completed`, только клиент заказа, один отзыв на заказ и идемпотентность повтора; корректность среднего качества, опыт включая заказы без отзывов, надёжность только по опубликованным и не скрытым Admin отзывам (§9.3.2), отсутствие оценок/коэффициентов при отсутствии видимых отзывов; числовой тест: три завершённых заказа и три отзыва — видимый 5 звёзд с отметкой «Соблюдал договорённости», скрытый 1 звезда без отметки, видимый 4 звезды без отметки; публичные `workQuality = 4.5`, `reliability = 1/2`, `reviewsCount = 2`, `experience = 3`; после скрытия обоих оставшихся видимых отзывов `reviewsCount = 0`, `workQuality` и `reliability` не имеют значения (не подменяются нулём или фиктивной оценкой), `experience = 3`; отсутствие влияния на фильтр ленты/допуск мастера; история 60/изменяемый Admin-лимит и локальное скрытие без уничтожения канонических фактов. Модерация: публикация без предварительного одобрения, скрытие только Admin с основанием и аудитом, неизменность оценки/текста/отметок и сохранение оригинала при скрытии; скрытый отзыв исключён из публичного списка, `workQuality`, `reliability` и `reviewsCount`, но не влияет на `experience`; случай скрытия единственного публичного отзыва не создаёт фиктивной средней оценки; отсутствие произвольной предварительной проверки.

**Тесты уведомлений и сообщений:** подходящий новый заказ → событие только мастеру с соответствующей выбранной специализацией; новый отклик → событие клиенту; исключённый мастер не получает повторных уведомлений о том же `job_id`; закрытие заказа и чужих чатов адресуется только участникам; ожидание ответа во временном чате → напоминание только ожидаемой стороне; инварианты cancellation/inactivity deadlines; отключённый звук ОС не меняет бизнес-состояние; настройки пользователя не становятся фильтром заказов; повторная доставка идемпотентна; уведомление не раскрывает скрытый адрес и чужие сообщения; Platform Inbox и Feedback не смешиваются с заказным чатом и Resolution. Для официального Support Chat: только Admin вправе начать беседу от имени Helpy; Master/Client получают сообщение от подтверждённой службы и отвечают ей; чужой профиль и поддельный Helpy отклоняются; контекст обращения валиден; после закрытия Job история Support Chat сохраняется; локализация/перевод не переписывают оригинал; текст «долг погашен» не уменьшает долг, не закрывает Resolution и не изменяет финансовый ledger; повторная доставка сообщения не создаёт новый чат или изменение баланса.

**Раздельные разрешения:** до явной приёмки контракта владельцем (`DOCUMENT GATE`) не направлять задание SOL, не начинать реализацию и не переносить контракт в репозиторий. После утверждения и передачи задания SOL реализует F2 в согласованном локальном рабочем дереве `Helpy-Clean` и предъявляет доказательства §12.2–§12.3 для приёмки результата (`CODE GATE`). Принятие документа не является приёмкой кода или автоматическим разрешением на commit/push. Commit, push, публикация или изменение состояния GitHub допускаются только по отдельному разрешению владельца; до него результат остаётся локальным. Не отменять чужие изменения.
